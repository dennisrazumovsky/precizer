# План изменений для поддержки конфигурационного файла

Документ задаёт согласованные требования и порядок реализации поддержки конфигурационного файла

## Основные постулаты

Дальнейшие требования и этапы реализации развивают следующие положения

1. **Один источник настроек**. Значения по умолчанию задаются один раз. Рабочие настройки поступают либо из файла, либо из CLI. Между этими источниками нет приоритета, объединения списков или переопределения значений
2. **Предсказуемый выбор файла**. Без аргументов CLI автоматически используется `precizer.conf` из текущей директории, если он существует. Для выбора другого файла служат `--config` и `-g`. Обычный CLI-запуск без выбора файла вообще не открывает и не проверяет стандартную конфигурацию
3. **Выбор файла исключает остальные CLI-аргументы**. Сочетание `--config` или `-g` с рабочими опциями, позиционными путями, информационными параметрами или самостоятельным `--` вызывает конфликт до чтения файла и применения настроек. Значение опции выбора файла посторонним аргументом не считается. Конфликт проверяется после успешного предварительного прохода; синтаксические ошибки передаются обычному обработчику CLI
4. **Выбранный источник описывает весь запуск**. Для выполнения сканирования или сравнения все обязательные настройки должны находиться в выбранном источнике. Повторы обрабатываются внутри него: одиночное значение заменяется последним, списки накапливаются, флаги выполняют согласованные действия. Недостающие параметры из другого источника не берутся
5. **Простой формат файла**. Конфигурация состоит из записей `ключ = значение` без секций, с комментариями `#`. Имена ключей соответствуют длинным CLI-опциям без `--`. Повторяемые записи и строки продолжения позволяют задавать несколько значений. Файл должен позволять самостоятельно настроить как сканирование, так и сравнение
6. **Один механизм применения параметров**. inih читает файл, argp разбирает CLI, а значения выбранного источника применяются общей функцией `apply_option()` на основе существующих ветвей `switch`. Используются одна таблица `options[]` и один `Config`. Существующие проверки и действия переиспользуются; отдельный обработчик для каждой опции не создаётся
7. **Минимально необходимые изменения**. Работа строится на существующих механизмах программы с согласованными ниже уточнениями поведения. Перед выполнением операции проверяется итоговая конфигурация; настройки другой операции очищаются до нормализации и диагностического вывода. Полноценная поддержка multi-root и перестройка рабочего алгоритма не входят в этот план
8. **Внедрение по одному элементу**. Каждый подготовительный шаг и каждый аргумент, добавляемый в конфигурационный файл, проходят отдельную проверку пользователем. Один шаг поддержки аргумента включает необходимые изменения кода, документацию в комментариях `precizer.conf`, конфигурационные файлы выбранных тестов и дополнение этих тестов файловыми запусками. После проверки тестов работа останавливается до явного разрешения перейти дальше. Выбор тестов и порядок добавления аргументов заранее фиксируются в отдельном плане

## 1 Согласованные требования

1. **Охват параметров**. Все параметры, которые сейчас передаются через командную строку, должны поддерживаться в конфигурационном файле, кроме информационных параметров `help`, `usage`, `version` и служебного параметра `config`. Эти четыре параметра доступны только в CLI. Корни сканирования, режим сравнения и пути к обеим сравниваемым базам поддерживаются в конфигурационном файле
2. **Один источник рабочих настроек**. После инициализации значениями по умолчанию выбрать файл либо CLI по пунктам 3 и 8. Разобрать и применить только выбранный источник в порядке его обработки. Значения из файла и CLI не объединяются и не переопределяют друг друга. Повторы внутри одного источника сохраняют свои правила: для одиночных значений вроде `maxdepth`, `database`, `compare-first` и `compare-second` действует последнее прочитанное значение, значения списочных параметров накапливаются, флаги выполняют действия по пункту 12. При синтаксической ошибке предварительного прохода файл не читать, а диагностику поручить основному обработчику CLI по пункту 3 раздела 2
3. **Автоматическое обнаружение и относительные пути**. Имя конфигурационного файла формируется из `APP_NAME` и суффикса `.conf`: для precizer это `precizer.conf`. Искать и автоматически читать его в текущей рабочей директории только при запуске без аргументов CLI, то есть при исходном `argc == 1`. Любые аргументы CLI, включая позиционные пути, информационные параметры и разделитель `--`, отключают автоматическое чтение. При таком запуске без явного `--config` стандартный файл вообще не открывать, не проверять на наличие или доступность и не разбирать; его содержимое и ошибки не влияют на запуск. Относительные пути из используемого файла разрешаются относительно рабочей директории запуска, как пути из CLI, в том числе при расположении файла в другой директории
4. **Отключение и сброс настроек через CLI**. В CLI не добавляются новые отрицательные флаги, формы передачи `false` для отключения флагов, параметры сброса к значениям по умолчанию и очистки списков
5. **Пути в конфигурационном файле**. Для корней сканирования используется повторяемый параметр `path`. Каждая строка со значением содержит один путь, а несколько таких строк задают список корней сканирования
6. **Формат без секций**. Новая запись конфигурационного файла начинается со строки вида `ключ = значение`. Разделителем ключа и значения служит только `=`; форма `ключ:значение` недопустима. Строки продолжения оформляются по правилам пункта 13. Комментарий начинается с `#` и продолжается до конца строки. Символ `;` не начинает комментарий. Секции не используются
7. **Повторяемые ключи**. Один и тот же ключ может встречаться в файле несколько раз. Для `path`, `ignore`, `include` и других параметров, поддерживающих несколько значений, каждая запись добавляет отдельное значение в список. Значения CLI-параметров со списком также накапливаются внутри CLI-запуска
8. **Явный выбор конфигурационного файла**. Добавить служебный параметр `--config=FILE` с короткой формой `-g FILE`. Поддерживать также `--config FILE` и `-gFILE`. Выбор файла несовместим с любыми другими CLI-опциями, включая информационные, позиционными аргументами и самостоятельным разделителем `--`. После успешного предварительного прохода такое сочетание вызывает ошибку конфликта до открытия файла, применения настроек и вывода справки. Значение самой опции выбора файла посторонним аргументом не считается. Повторение только `--config` и `-g` разрешено: использовать последний путь и читать только этот файл. Стандартный файл дополнительно не читать и при ошибке выбранного файла к нему не переходить. Относительный путь к файлу разрешается относительно текущей рабочей директории. Во всём документе правила для `--config` распространяются и на `-g`
9. **Обязательные параметры**. Для выполнения сканирования требуется хотя бы один корень, для сравнения — пути к двум базам по пункту 10. Проверять их наличие после полного разбора выбранного источника. Если обязательных путей недостаточно, формировать ошибку с тем же текстом и оформлением, что и в аналогичном запуске только с CLI. Исключения для пустого запуска и информационных параметров определены в пунктах 24 и 25
10. **Сравнение баз данных**. В файловом запуске режим включается записью `compare = true`, а оба пути задаются ключами `compare-first` и `compare-second` в том же файле. К `compare` применять общие правила флагов из пункта 12. В CLI-запуске режим включается через `--compare`, а пути задаются одним из двух взаимоисключающих способов: полной именованной парой `--compare-first` и `--compare-second` либо ровно двумя позиционными аргументами в порядке «первая база, вторая база», как в `precizer --compare FIRST_DB SECOND_DB`. При включённом сравнении наличие в CLI хотя бы одного именованного пути вместе хотя бы с одним позиционным считать ошибкой. Неполная именованная пара и количество позиционных путей, отличное от двух при отсутствии именованных, также являются ошибками. Проверять это после полного разбора выбранного источника. Параметры `path` и `--path` не используются для передачи сравниваемых баз
11. **Имена ключей**. Использовать длинные имена параметров CLI без начальных `--`, сохраняя дефисы: например, `maxdepth`, `one-file-system`, `dry-run`
12. **Логические значения флагов**. В конфигурационном файле принимать `true`, `yes`, `on`, `t`, `y`, `1` как логическую истину и `false`, `no`, `off`, `f`, `n`, `0` как логическую ложь. Регистр букв не учитывать, пробелы вокруг значения игнорировать. Истинное значение вызывает то же действие, что и соответствующий CLI-флаг без аргумента. Запись с ложным значением пропускается: она не меняет состояние флага и связанных настроек, заданное значениями по умолчанию или предыдущими записями. Например, после `progress = true` запись `progress = false` оставляет флаг включённым. Для `dry-run` дополнительно поддерживать значение `with-checksums` с тем же действием, что и `--dry-run=with-checksums`
13. **Строки продолжения**. Поддерживать запись дополнительных значений на следующих строках с отступом из пробелов или табуляции. Строки с ключом начинать без отступа. Каждую строку продолжения обрабатывать как повтор предыдущего ключа с отдельным значением, применяя существующие правила этого параметра. Для `ignore`, `include`, `path` и других параметров со списком каждая такая строка добавляет отдельный элемент. Пустые строки и комментарии значений не добавляют
14. **Документированный файл по умолчанию**. Создать `precizer.conf` в корне проекта при подключении чтения конфигурации. Добавлять описание и пример каждого аргумента одновременно с его поддержкой, по порядку раздела 3. К завершению внедрения сохранить в файле все приведённые в этом документе примеры, включая строки продолжения и эквивалентную запись с повторением ключа. Для каждой поддерживаемой настройки привести пример, назначение, допустимые значения, поведение по умолчанию и существенные условия применения. Источниками пояснений служат `README.ru.md`, `README.md` и описания параметров для `--help` в `src/parse_arguments.c`. Примеры настроек поставлять закомментированными с помощью `#`, чтобы они не применялись при автоматическом чтении файла. Параметры, доступные только в CLI, описать в комментариях с примерами команд

15. **Накопление корней сканирования**. При файловом запуске записи `path` добавляются в один массив `Config.roots` в порядке появления в файле. При CLI-запуске значения `--path` и позиционные корни добавляются в тот же массив в порядке их обработки argp; совместное использование этих двух форм внутри CLI разрешено. Наличие обязательных корней проверять по итоговому массиву. Сохранять текущую нормализацию и повторяющиеся элементы по пункту 22. В режиме сравнения очистить `Config.roots` после полного разбора выбранного источника, до нормализации, проверки доступности и вывода настроек. Наличие `path` или `--path` при сравнении само по себе не является ошибкой. Позиционные аргументы CLI в этом режиме обозначают базы данных и обрабатываются отдельно по пункту 10
16. **Параметр database при сравнении**. В файловом запуске с включённым сравнением игнорировать `database`, очищая сохранённое значение в памяти. В CLI-запуске сочетание `--database` или `-d` с `--compare` считать ошибкой несовместимости независимо от порядка аргументов. При сканировании применять значение `database` из выбранного источника. Игнорирование файловой настройки не отменяет проверки её значения при чтении файла
17. **Необязательный фильтр сравнения**. Параметр `compare-filter` разрешён в выбранном источнике независимо от режима. Сам фильтр необязателен, но каждая его запись или CLI-опция должна содержать одно из значений `checksum-mismatch`, `first-source`, `second-source`. При сравнении применять объединение категорий, заданных повторениями в одном источнике; при полном отсутствии фильтра использовать все три категории. При сканировании допустимый фильтр не включает сравнение; после полного разбора выбранного источника сбросить `Config.compare_filter` в `CF_NONE_SPECIFIED`, чтобы он не влиял на работу и вывод итоговых настроек
18. **Именованные пути к сравниваемым базам**. Использовать ключи `compare-first` для первой базы и `compare-second` для второй. Добавить соответствующие CLI-параметры `--compare-first=FILE` и `--compare-second=FILE`. Каждый параметр задаёт один путь: последнее значение в выбранном источнике заменяет предыдущее, а повторение не добавляет новую базу. Проверять наличие обоих путей и, для CLI, отсутствие позиционных путей только при включённом сравнении по пункту 10. Категории фильтра `first-source` и `second-source` относятся соответственно к первой и второй базам
19. **Доступность и ошибки чтения конфигурационного файла**. Проверять только выбранный файл после успешного предварительного прохода и отсутствия конфликта источников. При запуске без CLI отсутствие стандартного `precizer.conf` допускается; найденный, но недоступный для чтения стандартный файл вызывает ошибку. Если явно выбранный файл отсутствует или недоступен для чтения, завершить запуск с ошибкой. Если чтение началось, но завершилось ошибкой, остановить запуск; продолжать работу с частично прочитанными настройками нельзя
20. **Пути сравнения без включённого режима**. Параметры `compare-first` и `compare-second` сами не включают сравнение. Если после полного разбора выбранного источника режим сравнения не включён, очистить оба значения в памяти, в `Config`. Наличие одного или обоих параметров само по себе не вызывает ошибки или предупреждения. Эти базы не открывать и не проверять на доступность. Очистка не отменяет проверку синтаксиса и значений при разборе; корни сканирования по-прежнему обязательны
21. **Сообщения об ошибках**. Для ошибок, имеющих аналог в CLI, использовать существующий текст сообщения CLI. При ошибке конкретной записи конфигурационного файла добавлять расположение записи: путь к файлу и исходный номер строки. Сохранять действующую диагностику ошибок CLI и правило для отсутствующих обязательных параметров из пункта 9. Новые сообщения без аналога в CLI писать на US English в общем стиле диагностики программы: объяснять причину ошибки и при необходимости давать короткую подсказку по исправлению. В новых сообщениях о недопустимом значении указывать имя настройки, полученное значение и допустимые варианты; при превышении длины строки — установленный предел. При смешивании именованных и позиционных путей сравнения внутри CLI сообщать о несовместимости и указывать обе допустимые формы передачи. При конфликте `--config` с другими аргументами сообщать, что настройки должны задаваться либо файлом, либо CLI. Точные формулировки определять при реализации без отдельного согласования и закреплять в полных golden-шаблонах
22. **Несколько корней и дальнейшее развитие multi-root**. Наличие нескольких корней в `Config.roots` допускается и само по себе не является ошибкой конфигурации или CLI. На этапе этого плана сохранять существующий последовательный обход элементов массива, включая повторный обход повторяющихся корней, и действующее поведение БД. Такой способ передачи путей предусматривает дальнейшее развитие multi-root. Полноценный раздельный учёт файлов разных корней, изменение схемы БД, исправление очистки записей и обработку повторов реализовать на отдельном этапе развития программы; эти работы не входят в текущий план и не являются условием его завершения
23. **Очистка настроек другой операции**. После полного разбора выбранного источника очищать в памяти настройки, неприменимые к выбранному режиму, по разделу 2.2. Освобождать ненужные строки и массивы, а скалярные поля и связанные признаки возвращать к значениям по умолчанию. Правило действует для файлового и CLI-запуска независимо от порядка параметров внутри источника. Очистку выполнять до вывода итоговой конфигурации: неиспользуемые настройки не должны менять диагностический вывод и golden-шаблоны относительно запуска без них. Содержимое файла не изменять. Очистка не отменяет проверок синтаксиса и значений, несовместимостей из пунктов 10 и 16 и обязательных параметров выбранной операции
24. **Пустой запуск и неполные настройки**. Если аргументов CLI нет, а стандартный файл отсутствует, пуст или содержит только пустые строки и комментарии, показывать краткую справку и завершаться успешно, как при текущем запуске `precizer` без аргументов. Если используемый файл содержит записи настроек, но обязательных путей недостаточно, завершаться ошибкой по пункту 9. Запись с ложным значением флага тоже считается записью настройки, хотя её действие пропускается. Явный `--config=FILE` при недостатке обязательных путей также приводит к ошибке; пустой выбранный файл не превращает запуск в успешный показ справки. Если файл задаёт всё необходимое, выполнять операцию. Запуск с одним `--` не является пустым запуском. Информационные параметры обрабатывать по пункту 25
25. **Информационные параметры**. Параметры `--help`, `--usage` и `--version` не требуют корней сканирования или путей сравниваемых баз и не запускают эти операции. Стандартный файл при них не читать независимо от его содержимого и доступности. Сочетание любого информационного параметра с `--config` после успешного предварительного прохода вызывает ошибку конфликта до чтения файла и вывода справки или версии. При синтаксической ошибке предварительного прохода применять исключение из пункта 3 раздела 2: файл не читать, исходный CLI передать обычному обработчику

Выбор источника настроек:

| Запуск | Источник после значений по умолчанию или результат |
|---|---|
| `precizer` | Стандартный `precizer.conf`, если он есть |
| `precizer /data` или `precizer --update /data` | Только CLI; стандартный файл не проверяется и не читается |
| `precizer --help`, `precizer --usage` или `precizer --version` | Только CLI; стандартный файл не проверяется и не читается |
| `precizer --` | Только CLI; отсутствие обязательных путей является ошибкой |
| `precizer --config=task.conf` или `precizer -g task.conf` | Только выбранный файл; все обязательные параметры задаются в нём |
| `precizer --config=task.conf --maxdepth=3` | Конфликт источников до чтения файла |
| `precizer --config=task.conf /data` | Конфликт источников до чтения файла |
| `precizer --config=task.conf --help` | Конфликт источников до чтения файла и вывода справки |
| `precizer --config=task.conf --` | Конфликт источников до чтения файла |

Таблица предполагает синтаксически корректный CLI; при ошибке предварительного прохода действует пункт 3 раздела 2. Во всём документе значения и ошибки файла относятся только к файлу, выбранному по этим правилам. Опция выбора файла и её значение являются служебными аргументами и не добавляют рабочие CLI-настройки

Правила применения `compare-filter` внутри выбранного источника:

| Настройка `compare-filter` | Режим сравнения | Режим сканирования |
|---|---|---|
| Не указана в выбранном источнике | Сравнение по всем трём категориям | Обычное сканирование |
| Допустимое значение | Применить фильтр | Очистить в памяти до вывода настроек |
| Несколько допустимых значений через повторение параметра | Объединить категории; одинаковые значения допустимы | Очистить в памяти до вывода настроек |
| В файле `compare-filter =` | Ошибка | Ошибка |
| В CLI `--compare-filter=` | Ошибка | Ошибка |
| В CLI `--compare-filter` без обязательного значения | Ошибка | Ошибка |
| Недопустимое значение | Ошибка | Ошибка |

Каждое повторение проверять отдельно: пустое, отсутствующее у явно указанной опции или недопустимое значение считать ошибкой независимо от режима. Последующее корректное значение не исправляет предыдущую ошибку

Пример сравнения, полностью заданного в конфигурационном файле:

```ini
compare = true
compare-first = /mnt/storage/first.db
compare-second = /mnt/backup/second.db
```

При этих настройках в `precizer.conf` достаточно запуска `precizer` без аргументов. Другой файл с полным набором настроек можно выбрать через `precizer --config=profiles/compare.conf` или `precizer -g profiles/compare.conf`. Для изменения одной из баз изменить соответствующую запись выбранного файла либо передать полный набор параметров отдельным CLI-запуском без `--config`

Примеры записи флагов:

```ini
# Параметры запуска
progress = YES # Показывать прогресс
update = 1
dry-run = false
```

В этом примере `progress` и `update` включаются, а запись `dry-run` пропускается. Она не меняет ранее установленный режим пробного запуска

Пример нескольких путей и правил фильтрации в файле:

```ini
path = /mnt/storage1
path = /mnt/storage2
ignore = ^cache/
ignore = ^tmp/
include = ^cache/keep/
include = ^tmp/keep/
```

Пример значений `ignore` со строками продолжения:

```ini
ignore = ^cache/
    ^tmp/
    ^something_eles/

ignore = ^other/
    ^things/
```

Эквивалентная запись с повторением ключа:

```ini
ignore = ^cache/
ignore = ^tmp/
ignore = ^something_eles/
ignore = ^other/
ignore = ^things/
```

В обоих случаях в список `ignore` добавляются пять отдельных выражений в указанном порядке. Оба примера сохранить в корневом `precizer.conf` с пояснением их эквивалентности

Пример выбора другого конфигурационного файла:

```sh
precizer --config=profiles/archive.conf
precizer -g profiles/archive.conf
```

Обе команды используют только настройки указанного файла. Например, глубину сканирования следует задавать в нём записью `maxdepth = 2`

## 2 Требования к реализации

1. **Разбор с помощью inih и одна таблица параметров**. Использовать библиотеку inih из `libs/inih` для чтения записей `ключ = значение` без секций. Применять параметры библиотеки из раздела 2.1. Каждую строку продолжения inih передаёт отдельным вызовом обработчика с предыдущим ключом. Имена параметров и соответствующие им ключи обработчика брать из существующей таблицы `options[]`: искать точное длинное имя, включая поддерживаемые алиасы. Отдельный словарь параметров для файла не создавать
2. **Один общий обработчик значений**. Ветви существующего `switch` в `parse_opt()`, проверяющие и применяющие значения опций, перенести одним блоком в одну общую функцию `apply_option()`. Вызывать её из основного обработчика CLI и обработчика записей inih. Сохранить существующие проверки, присваивания и связанные действия параметров; отдельную функцию для каждой опции не создавать. Выбранный источник заполняет один существующий `Config`. Обработчик файла переводит файловые логические значения в действие флага или пропуск записи по разделу 1. Для ошибок использовать одну небольшую общую функцию диагностики: сохранять текст CLI, а при чтении файла добавлять его путь и текущую строку по пункту 21 раздела 1. Контекст источника нужен для текущего вызова, без хранения происхождения каждого значения. Момент проверки регулярных выражений определён пунктом 12 этого раздела; исключение для `database` при сравнении — пунктом 16 раздела 1. События argp, информационные параметры, служебный `--config`, позиционные аргументы и итоговые проверки оставить в обработчиках CLI
3. **Два прохода argp с одной таблицей параметров**. Использовать существующую `options[]` для предварительного и основного разбора CLI. Предварительный проход выполнять с `ARGP_SILENT`: сохранять путь из `--config` или `-g` и признак наличия других аргументов, не применяя настройки, не проверяя их значения и не выводя сообщений или справки. Аргумент самой опции выбора файла посторонним не считать; самостоятельный разделитель `--` учитывать как другой аргумент. После успешного прохода отклонить сочетание выбора файла с другими аргументами до открытия файла и применения настроек. Затем выбрать источник: явно указанный файл, стандартный файл при исходном `argc == 1` либо только CLI. Для файлового запуска полностью прочитать и применить файл. Основной проход argp сохраняется и в этом случае: в исходном CLI нет рабочих параметров, но его итоговые события проверяют уже заполненный `Config`. Если предварительный argp остановился на синтаксической ошибке, не разбирать её причину и не сообщать отдельно: отбросить частично найденные результаты, не читать файл и передать исходный CLI обычному обработчику для диагностики; операция не запускается. Такая диагностика имеет приоритет перед проверкой конфликта источников. В основном проходе опция выбора файла повторно распознаётся, но не читает файл и не меняет источник. Значения по умолчанию задавать один раз при инициализации
4. **Проверка итоговых настроек**. Проверять синтаксис и отдельные значения при разборе выбранного источника; для регулярных выражений применять порядок из пункта 12 этого раздела. Наличие обязательных параметров и их взаимосвязи проверять после полного разбора выбранного источника, до начала сканирования или сравнения баз данных. Учитывать исключения для пустого запуска и информационных параметров по пунктам 24 и 25 раздела 1
5. **Разделение настроек и рабочего состояния**. Использовать файл для описания параметров запуска. Управление соединениями с базами данных, скомпилированными регулярными выражениями, состоянием транзакций и другими рабочими ресурсами оставить в программе
6. **Совместимость существующих запусков**. Сохранить существующее поведение запусков только с рабочими CLI-аргументами независимо от наличия и содержимого стандартного файла, с учётом правил для `database`, `compare-filter` и очистки настроек другой операции из пунктов 16, 17 и 23 раздела 1. Обеспечить сканирование и сравнение без рабочих CLI-параметров, если автоматически или явно выбранный файл задаёт всё необходимое. Пустой запуск, неполные настройки, информационные параметры и конфликт источников обрабатывать по разделу 1
7. **Общее добавление корней**. Добавить повторяемый параметр `--path=PATH` и его обработку в `apply_option()`. Для `path` из файла, `--path` и позиционных корней CLI использовать эту же обработку добавления одного пути в `config->roots` с одинаковыми проверками значения. Позиционные аргументы направлять в неё из `parse_opt()` только в режиме сканирования. Сохранять порядок обработки существующего argp: порядок смешанных опций и позиционных аргументов может отличаться от их расположения в командной строке. Пустой путь не является допустимым корнем и не означает очистку массива
8. **Игнорирование файлового database**. Использовать общий признак выбранного источника, без отдельного отслеживания CLI-указания `--database`. После полного разбора при сравнении в файловом запуске очистить сохранённые в памяти путь основной базы и производное имя до вывода настроек. Существующий `db_determine_name()` затем выберет служебную базу `:memory:`. В CLI-запуске сохранять ошибку несовместимости явно заданного `--database` или `-d` с режимом сравнения
9. **Применение compare-filter**. Накапливать категории выбранного источника в существующем поле `config->compare_filter`. После полного разбора сохранять их при сравнении, а при сканировании сбрасывать поле в `CF_NONE_SPECIFIED` до диагностического вывода. Удалить проверку, запрещающую корректный фильтр без сравнения; проверки обязательного значения опции, допустимых категорий и обязательных путей сохранить
10. **Подготовка операндов сравнения**. Именованные пути первой и второй баз сохранять в отдельных полях с заменой при повторении в выбранном источнике; позиционные пути CLI накапливать в существующем массиве `db_file_paths`. После полного разбора при включённом сравнении отклонить сочетание любого именованного пути с любым позиционным внутри CLI. Для именованной формы проверить оба пути и заполнить ими `db_file_paths` в порядке «первая база, вторая база»; для позиционной формы проверить ровно два элемента массива. Дальнейшая обработка использует этот массив, как существующий код сравнения. Если сравнение не включено, освободить значения именованных путей и очистить соответствующие поля `Config` до нормализации и вывода настроек. Не очищать их до завершения разбора выбранного источника: включение сравнения может встретиться позднее в нём

11. **Учёт записей файла для пустого запуска**. В локальном контексте разбора хранить признак наличия хотя бы одной записи настройки в файле. Пустые строки и комментарии его не устанавливают; корректная запись флага с ложным значением устанавливает его до пропуска действия. Не определять наличие записей по итоговым значениям `Config`: они могут совпасть со значениями по умолчанию или быть очищены как неприменимые к выбранной операции. Использовать этот признак вместе с наличием аргументов CLI для правила пункта 24 раздела 1
12. **Простая проверка регулярных выражений**. Каждое выражение `ignore`, `include` и `lock-checksum` из файла, включая строки продолжения, проверять сразу при чтении временной компиляцией PCRE2. При ошибке прекращать чтение и выводить существующее сообщение с путём файла и исходным номером строки. При успехе сразу освобождать временный объект и добавлять копию строки в существующий список. Использовать небольшую общую функцию компиляции одного выражения с теми же параметрами PCRE2 и текстом ошибки, что в рабочей компиляции; расположение записи передавать только при проверке файла. Рабочую компиляцию итоговых списков оставить в существующем `compile_patterns()`. Не добавлять хранение происхождения каждого выражения, признаки выполненной проверки или кеш временных объектов; повторная компиляция при запуске принимается ради простоты кода. Для выражений CLI сохранить отложенную проверку при рабочей компиляции и ранний выход для информационных параметров. Единственное дополнение: после успешного разбора, если запуск продолжается для выполнения сравнения, перед очисткой `lock_checksum` проверить весь накопленный список выбранного источника той же временной компиляцией, даже если это уже проверенные записи файла, без признаков выполненной проверки

Эквивалентные способы передачи нескольких корней в режиме сканирования:

```sh
precizer /mnt/storage1 /mnt/storage2
precizer --path=/mnt/storage1 --path=/mnt/storage2
precizer --path=/mnt/storage1 /mnt/storage2
```

Во всех трёх примерах стандартный файл не читается. Для файлового запуска те же корни задаются в выбранном файле:

```ini
path = /mnt/storage1
path = /mnt/storage2
```

Запускать такую конфигурацию через `precizer` без аргументов, если это стандартный файл, либо через `precizer --config=FILE`. Передача дополнительных корней вместе с `--config` вызывает конфликт

Выбранный источник формирует массив корней и передаёт его существующему обходу по пункту 22 раздела 1. До отдельного этапа multi-root сохраняются известные ограничения: одинаковые относительные пути разных корней используют общую запись БД, а очистка при `--update` проверяет записи относительно одного корня. Эти ограничения принимаются по пункту 22 раздела 1; полноценная поддержка multi-root относится к отдельному проекту

### 2.1 Настройки inih

Определить параметры библиотеки через `#define` в основном заголовочном файле приложения `src/precizer.h` перед подключением `ini.h`. Значения параметров не передавать через аргументы компилятора и не дублировать в Makefile

```c
#define INI_MAX_LINE 4096
#define INI_STOP_ON_FIRST_ERROR 1
#define INI_HANDLER_LINENO 1
#define INI_ALLOW_MULTILINE 1
#define INI_ALLOW_INLINE_COMMENTS 0
#define INI_START_COMMENT_PREFIXES "#"
#define INI_USE_STACK 1
```

- `INI_MAX_LINE=4096` — фиксированный буфер размером 4096 байт. Допускать до 4093 байт содержимого каждой физической строки, оставляя место для `\r`, `\n` и завершающего нулевого байта. Ограничение применять к каждой строке продолжения отдельно. Более длинную строку отклонять с ошибкой, не применяя обрезанное значение
- `INI_STOP_ON_FIRST_ERROR=1` — прекращать разбор на первой ошибке и завершать запуск
- `INI_HANDLER_LINENO=1` — передавать номер строки обработчику. В сообщениях об ошибках записей указывать файл и номер строки
- `INI_ALLOW_MULTILINE=1` — поддерживать строки продолжения по пункту 13 раздела 1
- `INI_ALLOW_INLINE_COMMENTS=0` — отключить встроенную обработку комментариев после значения. Обработку `#` в любом месте строки выполнять в precizer при подготовке входных строк
- `INI_START_COMMENT_PREFIXES="#"` — использовать только `#` для комментариев на отдельных строках. Символ `;` сохранять как часть значения
- `INI_USE_STACK=1` — использовать фиксированный буфер на стеке без динамического выделения памяти для него

Остальные параметры inih оставить со штатными значениями по умолчанию

Определения из `src/precizer.h` должны действовать до первого подключения `ini.h` как в приложении, так и при компиляции реализации inih. Одного подключения заголовка в приложении недостаточно: `ini.c` собирается отдельно. В частности, `INI_HANDLER_LINENO` меняет число аргументов обработчика и должен совпадать у библиотеки и вызывающего кода

### 2.2 Очистка настроек по выбранной операции

Очищать только настройки, неприменимые к выбранной операции целиком. Отсутствие подходящих файлов или других условий для действия параметра в конкретном запуске не является основанием для общего сброса настроек

| Выбранная операция | Поля `Config` | Состояние после очистки |
|---|---|---|
| Сравнение | `roots` | Освободить элементы и хранилище массива, оставить корректный пустой массив с нулевой длиной |
| Сравнение | `maxdepth` | `-1`, как при инициализации |
| Сравнение | `force`, `quiet_ignored`, `watch_timestamps`, `one_file_system`, `db_drop_ignored`, `db_drop_inaccessible`, `rehash_locked` | `false` |
| Сравнение | `lock_checksum`, `lock_checksum_pcre_compiled` | Освободить выделенные ресурсы, оставить `NULL` |
| Сравнение | `progress`, связанный `show_remembered_messages_at_exit` | `false` до начала выполнения операции |
| Сравнение | `dry_run_with_checksums` | `false`; значение `dry_run` сохранить |
| Сравнение | `db_primary_file_path`, `db_file_name`, полученные из файлового `database` | Очистить по пункту 8 раздела 2; явный CLI-параметр `--database` или `-d` по-прежнему вызывает ошибку |
| Сканирование | Именованные пути `compare-first` и `compare-second`, массив `db_file_paths` и производные имена `db_file_names` | Освободить сохранённые значения, оставить пустые поля и массивы |
| Сканирование | `compare_filter` | `CF_NONE_SPECIFIED` |

При сравнении сохранять `ignore`, `include` и согласованный с ними `include_specified`: эти фильтры используются для отбора сравниваемых записей. Сохранять `db_check_level`, управляющий проверкой целостности обеих баз, и общие настройки вывода: `verbose`, `silent`, `color` и связанные настройки логирования

`update` и `dry_run` также сохранять: в текущем коде сравнение вызывает проверку версии БД и её обновление через `db_integrity_check()`, `db_check_version()` и `db_upgrade()`. Флаг `update` разрешает обновление старой версии, а `dry_run` влияет на проверку и операции с БД. Они не являются неиспользуемыми настройками обхода. При этом `dry_run_with_checksums` применяется только при чтении файлов: после его очистки в режиме сравнения `dry-run=with-checksums` остаётся обычным `dry-run` и так отображается в диагностике

Очистку выполнять в одном месте после полного разбора и проверок обязательных параметров и запрещённых сочетаний, до нормализации путей, создания производных имён, компиляции используемых шаблонов и вызовов `parse_arguments_show_testing_diagnostics()` и `parse_arguments_show_verbose_diagnostics()`. Не очищать настройки до завершения разбора выбранного источника: последующие записи или аргументы ещё могут влиять на итоговое состояние. Повторно вызывать `init_config()` или обнулять весь `Config` нельзя

Сохранить проверку значений перед очисткой. Перед удалением `lock_checksum` при сравнении проверить весь накопленный список по пункту 12 раздела 2. Эту проверку и очистку выполнять после раннего выхода для информационных параметров, чтобы сохранить существующее поведение CLI. Ошибки выражений из файла выявляются ещё при чтении и завершают файловый запуск

Предупреждения о `--db-drop-inaccessible` без `--update` и `--rehash-locked` без `--lock-checksum` проверять только при сканировании после определения режима. При сравнении соответствующие настройки очищаются и сами по себе не вызывают предупреждений. При сканировании сохранить существующие предупреждения и поведение этих сочетаний

Для управляемых массивов использовать существующие функции освобождения, сохраняющие корректное пустое состояние. Последующее освобождение `Config` должно оставаться безопасным. Не подменять очистку условным скрытием строк в функциях вывода

### 2.4 Порядок работы программы при запуске

Этот порядок описывает работу подключённого механизма конфигурации. Шаги его внедрения приведены в разделе 3

Организовать последовательность внутри `parse_arguments()`, которая уже вызывается после `init_config()`. В локальном контексте хранить путь конфигурации, признак других CLI-аргументов, выбранный источник и необходимые признаки разбора. Передавать контекст обработчикам argp через `argp_state.input`, обработчику inih — через пользовательский указатель. Рабочие значения выбранного источника применяются через одну `apply_option()`; предварительный проход их не применяет

1. Выполнить предварительный проход argp с той же таблицей, флагами `ARGP_SILENT` и отдельным обработчиком, сохраняющим выбранный путь и признак других аргументов. Передать копию массива указателей `argv`, поскольку argp может переставлять его элементы. Распознавать границы опций и их значений, не применяя настройки и не проверяя значения. Самостоятельный `--` учитывать как другой аргумент; если тот же текст является значением опции выбора файла, это имя файла
2. Если предварительный проход остановился на синтаксической ошибке, не анализировать и не выводить её отдельно. Отбросить частично найденные результаты, пропустить выбор и чтение файла в пунктах 3–4 и перейти к обычному разбору исходного CLI в пункте 5. Файл в этом случае не читается, операция не запускается
3. После успешного предварительного прохода проверить конфликт: если указан `--config` или `-g` и есть другие аргументы, завершить запуск с ошибкой до чтения файла и применения настроек. Иначе выбрать только явно указанный файл, только стандартный файл при исходном `argc == 1` либо только CLI. Для CLI-запуска перейти к пункту 5, не обращаясь к стандартному файлу
4. Для файлового запуска полностью прочитать и применить выбранный файл. Отсутствие автоматически выбранного стандартного файла и ошибки открытия или чтения обработать по пункту 19 раздела 1. При ошибке завершить запуск; явно выбранный файл не заменять стандартным
5. Выполнить основной проход argp по исходному CLI. В CLI-запуске `parse_opt()` передаёт рабочие опции в `apply_option()`. В файловом запуске рабочие настройки уже получены из файла, а основной проход встречает только служебные опции выбора файла либо пустой CLI; он нужен для существующих итоговых событий и проверок. Повторное распознавание `--config` или `-g` не читает файл и не меняет источник. При ошибке основного прохода завершить запуск без выполнения операции
6. В итоговых событиях основного прохода проверить настройки выбранного источника с учётом пустого запуска и информационных параметров по пунктам 24 и 25 раздела 1. При сканировании проверить корни, при сравнении — полноту именованной пары либо ровно два позиционных CLI-пути и запрет смешивания форм внутри CLI. Использовать адаптированный `ARGP_KEY_NO_ARGS` и существующий `ARGP_KEY_END`, сохранив сообщения отсутствующих обязательных параметров. Применить правило `database` по выбранному источнику. После успешного разбора и раннего выхода для информационных параметров очистить настройки другой операции по разделу 2.2, затем выполнить существующую нормализацию и вывод настроек
7. Освободить временные данные разбора при успешном завершении и при ошибке

### Конфигурационный повтор существующего теста

Существующий целевой CLI-запуск сохранить. Непосредственно после него и проверки его результата добавить один запуск той же операции через конфигурационный файл. Файл хранить рядом с golden-шаблонами в `tests/templates/`, используя номер теста и при необходимости номер сценария, например `NNNN_SSS.conf` рядом с `NNNN_SSS.txt`. В файловый запуск передавать только `--config=FILE` либо использовать стандартный файл, если проверяется автоматическое чтение; все рабочие настройки задавать в самом файле

Подготовку выполнять один раз существующими CLI-командами. Перед целевым CLI-запуском сохранить подготовленное состояние, которое операция изменяет. После проверки результата CLI восстановить это состояние и выполнить файловый запуск. Например, перед обновлением непустой БД сохранить её копию и восстановить её по тому же рабочему пути перед повтором обновления через файл. Если операция меняет другие данные, способ восстановления определить для конкретного теста. Если исходное состояние не меняется, копирование и восстановление не нужны. Повторно создавать исходную БД или выполнять всю подготовительную последовательность не требуется

Для эквивалентных CLI- и файлового запусков использовать один и тот же существующий полный golden-шаблон, одинаковые проверки результата и статуса завершения. Отдельную копию шаблона для файлового запуска не создавать. Оба запуска должны начинаться с одинакового состояния и приводить к одинаковому результату

Согласованные различия источников заранее отметить в индивидуальном плане: ошибки записей файла содержат его путь и строку по пункту 21 раздела 1, а `database` при сравнении обрабатывается по пункту 16. Такие случаи проверять по полному ожидаемому результату соответствующего источника; ради общего шаблона не удалять сведения об ошибке и не ослаблять сравнение. Ошибочные сценарии с одинаковой диагностикой используют общий golden-шаблон наравне с успешными

Перечни проверок в разделах ниже задают общее покрытие. Распределить их между шагами индивидуального плана, сохраняя по одному файловому повтору каждого уникального сценария. Повторное упоминание проверки в разных разделах не означает добавления ещё одного такого же запуска

### Сводная карта проверок

Это перечень требуемого покрытия для индивидуального плана, а не дополнительный этап внедрения. Общие механизмы проверять при их подключении, особенности аргументов — в соответствующих шагах. Повторный прогон существующего теста после изменения общей инфраструктуры не создаёт нового дублирующего сценария

Проверка применения значений: одинаковое применение соответствующих значений через CLI и обработчик inih, поиск длинных имён и алиасов по общей таблице, одиночные и повторяемые значения, порядок записей, все допустимые варианты логических значений и регистр букв, сохранение значения по умолчанию при ложной записи и сохранение включённого флага после последующей ложной записи, сохранение режима `dry-run=with-checksums` после записей `dry-run = true` и `dry-run = false`, копирование строк, ошибки формата и запрещённые ключи

Проверка регулярных выражений файла: корректные и ошибочные значения всех трёх параметров, повторяемые ключи и строки продолжения. Ошибка должна содержать путь файла, номер именно ошибочной строки и существующий текст PCRE2. Если ошибочное выражение предшествует другой недопустимой настройке, сообщать об выражении и прекращать чтение

Проверка синтаксиса: разделитель `=`, отклонение `ключ:значение` в начале новой записи, строки продолжения с пробелами и табуляцией, комментарии с `#` на отдельной строке и после значения, в том числе без предшествующего пробела. Проверить, что оба приведённых примера `ignore` дают одинаковые пять значений в одинаковом порядке. Символы `:` и `;` внутри значения сохраняются, в том числе в строках продолжения

Проверка ограничений и ошибок: строки на границе 4093 байт и сверх неё, включая строки продолжения и окончания строк LF и CRLF. Проверить отклонение слишком длинной строки без применения обрезанного значения, остановку на первой ошибке и правильное указание файла и исходного номера строки. Для одинаковой ошибки значения в CLI и файле проверить совпадение основного текста сообщения и добавление расположения записи только для файла, включая ошибку в строке продолжения. Новые сообщения проверить по пункту 21 раздела 1; в ошибке длины указывать предел содержимого строки 4093 байта

Проверка выбора источника: все случаи таблицы раздела 1, автоматическое чтение только без CLI, выбор стандартного и другого файла через `--config` и `-g`. Проверить формы `--config=FILE`, `--config FILE`, `-g FILE`, `-gFILE`, повторение длинной и короткой форм с чтением только последнего файла. Значение опции выбора файла не считается другим аргументом. Явно выбранный файл не объединяется со стандартным и не заменяется им при ошибке

Проверка конфликтов: сочетать каждую форму выбора файла с рабочей опцией, позиционным путём, `--help`, `--usage` и `--version`. Проверить оба порядка, повторные опции выбора файла и группы коротких опций. Конфликт выявляется до открытия файла, применения настроек и вывода справки или версии. Повторить сценарии с отсутствующим, недоступным и ошибочным выбранным файлом: результатом должен оставаться конфликт, файл не читается. Сообщение должно объяснять необходимость выбрать один источник

Проверка независимости CLI: запускать обычные команды без выбора файла при отсутствующем, корректном, недоступном и ошибочном стандартном файле. Оставленные в файле `compare`, `path`, `database`, `update`, флаги и фильтры не меняют операцию, параметры, диагностику и статус завершения CLI-запуска. Недостающие пути не дополняются из файла. Запуск с одним `--` не читает файл и выдаёт обычную ошибку отсутствующих путей. Подтвердить отсутствие обращений к стандартному файлу

Проверка передачи синтаксических ошибок основному проходу: неизвестная опция до и после выбора файла, отсутствие обязательного значения опции, `--maxdepth=bad --unknown`, `--help --unknown` и `--silent --unknown`. Предварительный проход не выводит сообщений и не применяет настройки; основной получает исходный CLI и сохраняет обычную диагностику. При ошибке предварительного прохода проверка конфликта источников не подменяет обычную диагностику CLI. Ни один файл не открывается, в том числе при повторном распознавании выбора файла основным проходом; операция не запускается

Проверка пустого запуска и обязательных путей: без CLI при отсутствии стандартного файла, пустом файле или файле только с комментариями и пустыми строками выводится краткая справка и возвращается успешный статус. Записи файла без необходимых путей вызывают ошибку, в том числе если все они содержат ложные значения флагов или настройки другой операции. Явно выбранный пустой файл также даёт ошибку отсутствующих путей. Полный набор настроек в стандартном или явно выбранном файле самостоятельно запускает сканирование или сравнение. Попытка дополнить неполный файл через CLI вызывает конфликт. Проверять полный вывод и статус завершения

Проверка информационных параметров: обычные `--help`, `--usage` и `--version` работают независимо от стандартного файла, не требуют обязательных путей и не запускают операции. Сочетание с выбором файла проверять как конфликт, без чтения файла и без вывода запрошенной справки или версии. Отдельно проверить отсутствие повторного вывода справки при двух проходах argp

Проверка регулярных выражений: ошибка в выбранном файле останавливает файловый запуск при чтении с указанием файла и строки. Обычный `--help` не читает стандартный файл с ошибочным выражением. Команды `--help --ignore="["` и `--help --lock-checksum="["` сохраняют показ справки без проверки CLI-выражений; то же правило действует для `--usage` и `--version`. При обычном CLI-сравнении ошибочный `--lock-checksum="["` вызывает ошибку до очистки списка, корректный список очищается. Корректные `ignore` и `include` работают при сканировании и сравнении, а `lock-checksum` — при сканировании; проверить отдельно файловый и CLI-запуск

Проверка доступности и чтения: без CLI отсутствие стандартного файла допускается, а его недоступность вызывает ошибку. Отсутствие или недоступность явно выбранного файла и ошибка чтения используемого файла завершают запуск. Проверить остановку и после чтения части настроек, без выполнения операции. При обычном CLI-запуске и при конфликте источников никакой конфигурационный файл не проверяется и не читается

Проверка корней: повторить CLI-сценарии этапа 3.5 после подключения выбора источника. Проверить накопление файловых `path` в порядке записей. Для обоих источников проверить отсутствие обязательных корней, нормализацию и сохранение повторяющихся элементов

Проверка сравнения: проверить CLI-сценарии именованных и позиционных путей вместе с внедрением аргументов сравнения на этапе 3.9. Полный файловый набор `compare = true`, `compare-first`, `compare-second` должен работать без CLI либо с выбором файла. Для файла проверить замену повторных именованных путей, неполную пару, включение `compare` до и после путей и сохранение включённого режима после `compare = false`. Стандартный файл с именованными путями не должен мешать обычному позиционному сравнению

Проверка путей сравнения при сканировании: один или оба именованных пути из выбранного источника очищаются в `Config`, не вызывают предупреждения и не проверяются на доступность. Проверить успешное сканирование с корнями и обычную ошибку при их отсутствии. Если тот же источник включает сравнение, именованные пути сохраняются и используются

Проверка очистки: при сравнении корни из файлового `path` либо CLI `--path` освобождаются, не проверяются на доступность и не попадают в вывод, а оба пути баз сохраняются. Для всех полей раздела 2.2 проверить состояние после очистки и совпадение полного вывода с запуском без настроек другой операции. Сценарии выполнять отдельно для файла и CLI; сочетать настройки и менять их порядок внутри источника. Проверить связанные признаки, отсутствие предупреждений из-за очищенных настроек и ошибки значений до очистки, включая PCRE2 для `lock-checksum`

Проверка сохраняемых настроек: сравнение продолжает учитывать `ignore`, `include`, `check-level`, `update`, `dry-run` и настройки вывода. Сохранить сценарии обновления старых БД при сравнении. Проверить, что `dry-run=with-checksums` при сравнении даёт те же действующие настройки и вывод, что обычный `dry-run`. При сканировании настройки обхода и существующие предупреждения об их зависимостях сохраняются

Проверка `database`: при файловом сравнении значение очищается, при CLI-сравнении явное указание вызывает ошибку в любом порядке аргументов. Отсутствие настройки не мешает сравнению. При сканировании применяется значение выбранного источника, при повторении — последнее

Проверка `compare-filter`: все случаи таблицы раздела 1 отдельно для файла и CLI, накопление категорий внутри источника, повторы одинаковых значений и остановка на пустом или недопустимом значении. При сканировании проверить сброс в `CF_NONE_SPECIFIED` и отсутствие фильтра в выводе. Сохранить требования к корням и двум операндам сравнения

### Проверка каждого этапа

После каждого согласованного шага, изменяющего код или тесты, запускать `make tests`. Эквивалентные CLI- и файловые запуски проверять по одному существующему полному шаблону; отдельные шаблоны использовать для новых сценариев и согласованных различий между источниками по пунктам 16 и 21 раздела 1. Файловые сценарии выполнять в изолированных рабочих директориях с существующими тестовыми помощниками и восстановлением подготовленного состояния по индивидуальному плану. Проверки выбора источника, независимости CLI и конфликта до чтения файла относятся к общей инфраструктуре и не дублируются для каждого аргумента. После проверки остановиться и передать результат пользователю; успешные тесты сами по себе не разрешают следующий шаг
