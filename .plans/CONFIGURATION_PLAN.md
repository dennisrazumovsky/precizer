# План изменений для поддержки конфигурационного файла

Документ задаёт согласованные требования и порядок реализации поддержки конфигурационного файла

Согласованные в ходе реализации изменения концепции и выявленные противоречия отражать в этом плане. Фиксировать фундаментальные правила поведения и границы задачи; технические подробности отдельных изменений в основной план не переносить

## Основные постулаты

Дальнейшие требования и этапы реализации развивают следующие положения

1. **Один источник настроек**. Значения по умолчанию задаются один раз. Рабочие настройки поступают либо из файла, либо из CLI. Между этими источниками нет приоритета, объединения списков или переопределения значений
2. **Предсказуемый выбор файла**. Без аргументов CLI автоматически используется `precizer.conf` из текущей директории, если он существует. Для выбора другого файла служат `--config` и `-g`. Обычный CLI-запуск без выбора файла вообще не открывает и не проверяет стандартную конфигурацию
3. **Выбор файла и информационные запросы**. Без информационного запроса сочетание `--config` или `-g` с другими CLI-опциями или позиционными путями вызывает конфликт до чтения файла и применения настроек. Запрос `--help`, `--usage`, `--version` или их коротких форм отключает выбор и чтение конфигурации, включая явно указанный файл; конфликт источников в этом случае не формируется. Предварительный проход только распознаёт запрос, а вывод информации и проверка остальных CLI-аргументов остаются в основном парсере. Значение опции выбора файла посторонним аргументом не считается. Ошибки предварительного прохода передаются обычному обработчику CLI
4. **Выбранный источник описывает весь запуск**. Для выполнения сканирования или сравнения все обязательные настройки должны находиться в выбранном источнике. Повторы обрабатываются внутри него: одиночное значение заменяется последним, списки накапливаются, последнее логическое значение флага в файле включает или выключает его. Недостающие параметры из другого источника не берутся
5. **Простой формат файла**. Конфигурация использует штатный синтаксис inih: записи `ключ = значение` или `ключ: значение`, комментарии `#` и строки продолжения. Значения можно заключать в одну пару одинаковых внешних кавычек по пункту 6 раздела 1. Секции разрешены как оформление файла и не влияют на смысл параметров. Имена ключей соответствуют длинным CLI-опциям без `--`. Повторяемые записи и строки продолжения позволяют задавать несколько значений. Файл должен позволять самостоятельно настроить как сканирование, так и сравнение
6. **Один механизм применения параметров**. inih читает файл, argp разбирает CLI, а значения выбранного источника применяются существующим обработчиком `parse_opt()`. Его `switch` сохраняется целиком. Используются одна таблица `options[]` и один `Config`. Существующие проверки и действия переиспользуются; отдельный обработчик для каждой опции не создаётся
7. **Минимально необходимые изменения**. Работа строится на существующих механизмах программы с согласованными ниже уточнениями поведения. Перед выполнением операции проверяется итоговая конфигурация, а рабочие функции учитывают выбранный режим. Полноценная поддержка multi-root и перестройка рабочего алгоритма не входят в этот план
8. **Внедрение по одному элементу**. Каждый подготовительный шаг и каждый аргумент, добавляемый в конфигурационный файл, проходят отдельную проверку пользователем. Один шаг поддержки аргумента включает необходимые изменения кода, документацию в комментариях `precizer.conf`, конфигурационные файлы выбранных тестов и дополнение этих тестов файловыми запусками. После проверки тестов работа останавливается до явного разрешения перейти дальше. Выбор тестов и порядок добавления аргументов заранее фиксируются в отдельном плане
9. **Сохранение существующего тестового покрытия**. Новые проверки конфигурации добавляются к исходным CLI-сценариям, сохраняя их условия запуска и проверки результата. Использование общих таблиц сценариев, помощников и golden-шаблонов не заменяет отдельного выполнения исходного сценария

## 1 Согласованные требования

1. **Охват параметров**. Все параметры, которые сейчас передаются через командную строку, должны поддерживаться в конфигурационном файле, кроме информационных параметров `help`, `usage`, `version` и служебного параметра `config`. Эти четыре параметра доступны только в CLI. Корни сканирования, режим сравнения и пути к обеим сравниваемым базам поддерживаются в конфигурационном файле
2. **Один источник рабочих настроек**. После инициализации значениями по умолчанию выбрать файл либо CLI по пунктам 3 и 8. Разобрать и применить только выбранный источник в порядке его обработки. Значения из файла и CLI не объединяются и не переопределяют друг друга. Повторы внутри одного источника сохраняют свои правила: для одиночных значений вроде `maxdepth` и `database` действует последнее прочитанное значение, значения списочных параметров накапливаются, флаги выполняют действия по пункту 12. При ошибке предварительного прохода файл не читать, а диагностику поручить основному обработчику CLI по пункту 3 раздела 2
3. **Автоматическое обнаружение и относительные пути**. Имя конфигурационного файла формируется из `APP_NAME` и суффикса `.conf`: для precizer это `precizer.conf`. Искать и автоматически читать его в текущей рабочей директории только при запуске без аргументов CLI, то есть при исходном `argc == 1`. Любые аргументы CLI, включая позиционные пути, информационные параметры и разделитель `--`, отключают автоматическое чтение. При таком запуске без явного `--config` стандартный файл вообще не открывать, не проверять на наличие или доступность и не разбирать; его содержимое и ошибки не влияют на запуск. Относительные пути из используемого файла разрешаются относительно рабочей директории запуска, как пути из CLI, в том числе при расположении файла в другой директории
4. **Отключение и сброс настроек через CLI**. В CLI не добавляются новые отрицательные флаги, формы передачи `false` для отключения флагов, параметры сброса к значениям по умолчанию и очистки списков
5. **Пути в конфигурационном файле**. Для корней сканирования используется повторяемый параметр `path`. Каждая строка со значением содержит один путь, а несколько таких строк задают список корней сканирования
6. **Формат файла**. Разделителем ключа и значения служит `=` или `:`. Строки продолжения оформляются по правилам пункта 13. Комментарий начинается с `#` в начале строки, в том числе после отступа, либо после значения при наличии пробельного символа перед `#`, и продолжается до конца строки. Например, `value # comment` содержит комментарий, а `value#suffix` целиком является значением. Символ `;` не начинает комментарий. Если значение начинается с `"` или `'`, оно должно заканчиваться такой же кавычкой: перед применением значения удалить только эту внешнюю пару. Без внешних кавычек значение использовать без изменений. Пробелы и обратные слеши внутри сохранять; подстановку переменных, исполнение команд, обработку escape-последовательностей и склейку частей как в shell не выполнять. Кавычки снимать до распознавания логических, числовых и остальных значений; пустое содержимое проверять по обычным правилам параметра. Незакрытую или закрытую другой кавычкой запись отклонять с номером строки. Это же правило действует отдельно для каждой строки продолжения. Комментарии обрабатывает inih до снятия кавычек, поэтому пробельный символ перед `#` начинает комментарий даже внутри кавычек. Секции разрешены, в том числе без записей и с пустым именем `[]`. Их заголовки пропускаются; все настройки обрабатываются в общем порядке файла. Одинаковые ключи в разных секциях подчиняются обычным правилам повторов и не сбрасывают уже накопленные значения
7. **Повторяемые ключи**. Один и тот же ключ может встречаться в файле несколько раз. Для `path`, `ignore`, `include` и других параметров, поддерживающих несколько значений, каждая запись добавляет отдельное значение в список. Значения CLI-параметров со списком также накапливаются внутри CLI-запуска
8. **Явный выбор конфигурационного файла**. Добавить служебный параметр `--config=FILE` с короткой формой `-g FILE`. Поддерживать также `--config FILE` и `-gFILE`. Без информационного запроса выбор файла несовместим с другими CLI-опциями и позиционными аргументами. После успешного предварительного прохода такое сочетание вызывает ошибку конфликта до открытия файла и применения настроек. При информационном запросе выбор файла игнорируется по пункту 25. Значение самой опции выбора файла посторонним аргументом не считается. Повторение только `--config` и `-g` разрешено: использовать последний путь и читать только этот файл. Стандартный файл дополнительно не читать и при ошибке выбранного файла к нему не переходить. Относительный путь к файлу разрешается относительно текущей рабочей директории. Во всём документе правила для `--config` распространяются и на `-g`
9. **Обязательные параметры**. Для выполнения сканирования требуется хотя бы один корень, для сравнения — пути к двум базам по пункту 10. Проверять их наличие после полного разбора выбранного источника. Если обязательных путей недостаточно, формировать ошибку в общем стиле диагностики CLI. При отсутствии корней сканирования явно сообщать, что требуется хотя бы один путь, и давать подсказку для выбранного источника: в конфигурационный файл добавить ключ `path`, например `path = /path/to/directory`; в CLI передать каталог позиционно или через `--path=PATH`. Одной краткой справки и общего сообщения об ошибке разбора недостаточно. Исключения для пустого запуска и информационных параметров определены в пунктах 24 и 25
10. **Сравнение баз данных**. В файловом запуске каждая запись `compare = PATH` включает сравнение и добавляет один путь к базе. Пути задаются повторением ключа или строками продолжения; требуется ровно два значения в порядке «первая база, вторая база». В CLI сохраняется форма `precizer --compare FIRST_DB SECOND_DB` с двумя позиционными путями. Проверять количество баз после полного разбора выбранного источника. Параметры `path` и `--path` не используются для передачи сравниваемых баз
11. **Имена ключей**. Использовать точные длинные имена параметров CLI без начальных `--`, сохраняя регистр и дефисы: например, `maxdepth`, `one-file-system`, `dry-run`. Сокращения имён и другие варианты регистра не принимать. Старые имена `db-clean-ignored`, `drop-inaccessible` и `start-device-only` исключены из плана внедрения: отдельные шаги, примеры в `precizer.conf` и файловые проверки для них не нужны. Существующую поддержку алиасов из общей таблицы CLI и их CLI-проверки сохранить
12. **Логические значения флагов**. Эти правила не относятся к файловому `compare`, который содержит пути по пунктам 10 и 20. В конфигурационном файле принимать `true`, `yes`, `on`, `y`, `1` как логическую истину и `false`, `no`, `off`, `n`, `0` как логическую ложь. Регистр букв не учитывать. Пробелы вокруг значения игнорировать до снятия кавычек; пробелы внутри кавычек сохранять по пункту 6. Истинное значение включает флаг, ложное выключает его. При повторении ключа действует последнее значение, в том числе в другой секции; значение по умолчанию сохраняется, если ключ не указан. Например, после `progress = true` запись `progress = false` выключает прогресс, а обратный порядок включает его. Связанные настройки должны соответствовать итоговому состоянию флага: отключение прогресса отключает и установленный им повторный вывод сохранённых сообщений перед завершением. Отключение действующего режима `silent` или `verbose` возвращает исходный режим вывода с учётом `TESTING`; отключение одного не отменяет другой действующий режим. Ранее вытесненный режим вывода автоматически не восстанавливается. Пустое значение и варианты вне перечисленных, включая `t` и `f`, считать ошибкой. Для `dry-run` дополнительно поддерживать значение `with-checksums` с тем же действием, что и `--dry-run=with-checksums`. Последняя запись полностью задаёт режим: `false` выключает пробный запуск и расчёт контрольных сумм в нём, `true` включает обычный пробный запуск без расчёта сумм, `with-checksums` включает оба действия
13. **Строки продолжения**. Использовать штатное правило inih: после записи ключа непустая строка с отступом из пробелов или табуляции считается продолжением его значения, кроме строк комментариев. Каждую строку продолжения обрабатывать как повтор предыдущего ключа с отдельным значением, применяя существующие правила этого параметра. Для `ignore`, `include`, `path`, `compare` и других параметров со списком каждая такая строка добавляет отдельный элемент. Новые ключи и заголовки секций в примерах писать без отступа, чтобы отличать их от продолжений; отдельную проверку отступа перед первым ключом не вводить. Пустые строки и комментарии значений не добавляют. Заголовок секции завершает продолжение предыдущего ключа, но не сбрасывает накопленные настройки
14. **Документированный файл по умолчанию**. Создать `precizer.conf` в корне проекта при подключении чтения конфигурации. Добавлять описание и пример каждого аргумента одновременно с его поддержкой, по порядку раздела 3. К завершению внедрения сохранить в файле все приведённые в этом документе примеры, включая строки продолжения и эквивалентную запись с повторением ключа. Описания всех настроек формировать на основе двух источников: справки `--help` и `README.md`, сохраняя их пользовательский смысл и адаптируя примеры для конфигурационного файла. Писать простым, понятным языком для пользователя без знаний программирования: объяснять, что делает настройка, когда она нужна, какой результат даёт и как её задать. В закомментированных строках настроек указывать фактические значения по умолчанию, если они представимы допустимым значением параметра. Рядом кратко перечислять допустимые значения или указывать их тип и диапазон; например, для логического флага — `true` или `false`, значение по умолчанию — `false`. Если значение отсутствует, вычисляется при запуске или поведение по умолчанию задаётся отсутствием настройки, явно описывать это в комментарии `Default`, а отдельные рабочие примеры помечать `Example`. Не подставлять вместо значения по умолчанию произвольный пример или внутреннее значение, которое парсер не принимает. Приводить наглядные примеры и пояснять существенные условия применения. Практический смысл важнее формального перечисления допустимых значений и правил разбора. Варианты значений и ограничения описывать только в объёме, необходимом для осознанного выбора настройки и правильного заполнения файла; внутреннее устройство программы и избыточные технические подробности в комментарии не переносить. Примеры настроек поставлять закомментированными с помощью `#`, чтобы они не применялись при автоматическом чтении файла. В поясняющих комментариях ставить пробел после `#`, а в примерах записей — писать ключ сразу после `#`, без пробела: `#database = /mnt/databases/storage.db`. Такое оформление визуально отделяет описание от примера настройки; отступы строк продолжения сохранять после `#`. Параметры, доступные только в CLI, описать в комментариях с примерами команд

15. **Накопление корней сканирования**. При файловом запуске записи `path` добавляются в один массив `Config.roots` в порядке появления в файле. При CLI-запуске значения `--path` и позиционные корни добавляются в тот же массив в порядке их обработки argp; совместное использование этих двух форм внутри CLI разрешено. Наличие обязательных корней проверять по итоговому массиву. Сохранять текущую нормализацию и повторяющиеся элементы по пункту 22. В режиме сравнения корни не проверяются на доступность и не обходятся; их обработка сохраняется по разделу 2.2. Наличие `path` или `--path` при сравнении само по себе не является ошибкой. Позиционные аргументы CLI в этом режиме обозначают базы данных и обрабатываются отдельно по пункту 10
16. **Параметр database при сравнении**. Сочетание `database` с режимом сравнения считать ошибкой для обоих источников независимо от порядка параметров. Сохранить существующее поведение CLI и применять его к файловому запуску. При сканировании использовать значение `database` из выбранного источника
17. **Необязательный фильтр сравнения**. Параметр `compare-filter` допустим только при включённом сравнении, как в CLI, так и в конфигурационном файле. Сам фильтр необязателен, но каждая его запись или CLI-опция должна содержать одно из значений `checksum-mismatch`, `first-source`, `second-source`. При сравнении применять объединение категорий, заданных повторениями в одном источнике; при полном отсутствии фильтра использовать все три категории. Указание фильтра без включённого сравнения вызывает ошибку
18. **Порядок путей сравнения**. Повторные записи `compare` добавляют пути, а не заменяют предыдущие. Строка продолжения также добавляет один путь. Категории фильтра `first-source` и `second-source` относятся соответственно к первому и второму элементам списка
19. **Доступность и ошибки чтения конфигурационного файла**. Проверять только выбранный файл после успешного предварительного прохода при отсутствии информационного запроса и конфликта источников. При запуске без CLI отсутствие стандартного `precizer.conf` допускается; найденный, но недоступный для чтения стандартный файл вызывает ошибку. Если явно выбранный файл отсутствует или недоступен для чтения, завершить запуск с ошибкой. Если чтение началось, но завершилось ошибкой, остановить запуск; продолжать работу с частично прочитанными настройками нельзя
20. **Значение compare в файле**. Это путь, а не логический флаг: `true`, `false` и другие похожие слова считаются именами файлов. Пустое значение недопустимо. Каждое значение целиком задаёт один путь, включая пробелы; общие правила внешних кавычек сохраняются. Несколько путей внутри одной строки не разделять. Для сканирования записи `compare` должны отсутствовать
21. **Диагностика настроек и ошибок**. Путь к используемому конфигурационному файлу выводить вместе с остальными настройками в `parse_arguments_show_verbose_diagnostics()` и `parse_arguments_show_testing_diagnostics()`, с сохранением условий вывода соответствующего режима. При запуске только с CLI поле пути конфигурации не выводить. Для ошибок, имеющих аналог в CLI, использовать существующий текст сообщения CLI, кроме уточнённой диагностики отсутствующих корней по пункту 9. В сообщении об ошибке разбора сразу после имени программы выводить `ERROR:`. При ошибке, обнаруженной при чтении записи конфигурационного файла, за ним добавлять `Line N in config file:`, где `N` — исходный номер ошибочной строки, например `precizer: ERROR: Line 12 in config file:`. Путь к файлу в сообщение об ошибке записи не включать. Ошибки регулярных выражений выявлять при рабочей компиляции с обычной диагностикой PCRE2 без номера строки файла по пункту 12 раздела 2. Сохранять действующую диагностику ошибок CLI с уточнением для отсутствующих обязательных параметров из пункта 9. Новые сообщения без аналога в CLI писать на US English в общем стиле диагностики программы: объяснять причину ошибки и при необходимости давать короткую подсказку по исправлению. В сообщениях о недопустимом значении сохранять подстановку ошибочного значения, если оно присутствует в существующем сообщении CLI. В новых сообщениях о недопустимом значении указывать имя настройки и допустимые варианты. При конфликте `--config` с другими аргументами сообщать, что настройки должны задаваться либо файлом, либо CLI. Точные формулировки новых сообщений, кроме согласованного префикса, определять при реализации без отдельного согласования и закреплять в полных golden-шаблонах
22. **Несколько корней и дальнейшее развитие multi-root**. Наличие нескольких корней в `Config.roots` допускается и само по себе не является ошибкой конфигурации или CLI. На этапе этого плана сохранять существующий последовательный обход элементов массива, включая повторный обход повторяющихся корней, и действующее поведение БД. Такой способ передачи путей предусматривает дальнейшее развитие multi-root. Полноценный раздельный учёт файлов разных корней, изменение схемы БД, исправление очистки записей и обработку повторов реализовать на отдельном этапе развития программы; эти работы не входят в текущий план и не являются условием его завершения
23. **Настройки вне своей операции**. Сохранить существующую обработку настроек, не относящихся к выбранному режиму, одинаковую для CLI и файла. Не требовать совпадения вывода запусков с разными наборами аргументов. Совпадение CLI и файла проверять для одинаковых настроек. Правила совместимости `database`, применения регулярных выражений и предупреждений определены в разделе 2.2
24. **Пустой запуск и неполные настройки**. Если аргументов CLI нет, а стандартный файл отсутствует, пуст или содержит только пустые строки, комментарии и заголовки секций, показывать краткую справку и завершаться успешно, как при текущем запуске `precizer` без аргументов. Если используемый файл содержит записи настроек, но обязательных путей недостаточно, завершаться ошибкой по пункту 9. Запись с ложным значением флага тоже считается записью настройки, даже если итоговое состояние совпадает со значением по умолчанию. Явный `--config=FILE` при недостатке обязательных путей также приводит к ошибке; пустой выбранный файл не превращает запуск в успешный показ справки. Если файл задаёт всё необходимое, выполнять операцию. Запуск с одним `--` завершается ошибкой по пункту 26. Информационные параметры обрабатывать по пункту 25
25. **Информационные параметры**. Параметры `--help` (`-h`, `-?`), `--usage` (`-z`) и `--version` (`-V`) не требуют корней сканирования или путей сравниваемых баз и не запускают эти операции. Предварительный проход только отмечает информационный запрос: стандартный и явно указанный файлы не проверяются и не читаются независимо от их содержимого, доступности и порядка аргументов. Выбор файла игнорируется, конфликт источников не формируется. Основной парсер сохраняет обычный вывод справки или версии и проверку остальных CLI-аргументов; информационный запрос не отменяет их синтаксические ошибки или ошибки значений. Предварительный проход ничего не печатает, поэтому сам по себе не создаёт повторного вывода. При его ошибке файл также не читать, а диагностику поручить основному парсеру по пункту 3 раздела 2

26. **Использование `--`**. Если библиотека argp отмечает использование `--` своим штатным признаком, завершать запуск с ошибкой `ERROR: Unsupported use of --`. Предварительный проход обнаруживает это без сообщения и исключает чтение конфигурации; основной выдаёт диагностику до проверки обязательных путей. Не искать строку `--` отдельным проходом по аргументам и не различать дополнительно разделитель и значение опции. Значения, которые библиотека не отмечает этим признаком, обрабатываются обычно; формы `--config=--` и `--config ./--` допускают файл с именем `--`

Выбор источника настроек:

| Запуск | Источник после значений по умолчанию или результат |
|---|---|
| `precizer` | Стандартный `precizer.conf`, если он есть |
| `precizer /data` или `precizer --update /data` | Только CLI; стандартный файл не проверяется и не читается |
| `precizer --help`, `precizer --usage` или `precizer --version` | Только CLI; стандартный файл не проверяется и не читается |
| `precizer --` | Ошибка `Unsupported use of --`; конфигурация не читается |
| `precizer --config=task.conf` или `precizer -g task.conf` | Только выбранный файл; все обязательные параметры задаются в нём |
| `precizer --config=task.conf --maxdepth=3` | Конфликт источников до чтения файла |
| `precizer --config=task.conf /data` | Конфликт источников до чтения файла |
| `precizer --config=task.conf --help` | Показ справки; выбор файла игнорируется, файл не проверяется и не читается |
| `precizer --config=task.conf --` | Ошибка `Unsupported use of --` до чтения файла |

Таблица предполагает синтаксически корректный CLI; при ошибке предварительного прохода действует пункт 3 раздела 2. Во всём документе значения и ошибки файла относятся только к файлу, выбранному по этим правилам. Опция выбора файла и её значение являются служебными аргументами и не добавляют рабочие CLI-настройки

Правила применения `compare-filter` внутри выбранного источника:

| Настройка `compare-filter` | Режим сравнения | Режим сканирования |
|---|---|---|
| Не указана в выбранном источнике | Сравнение по всем трём категориям | Обычное сканирование |
| Допустимое значение | Применить фильтр | Ошибка: фильтр требует включённого сравнения |
| Несколько допустимых значений через повторение параметра | Объединить категории; одинаковые значения допустимы | Ошибка: фильтр требует включённого сравнения |
| В файле `compare-filter =` | Ошибка | Ошибка |
| В CLI `--compare-filter=` | Ошибка | Ошибка |
| В CLI `--compare-filter` без обязательного значения | Ошибка | Ошибка |
| Недопустимое значение | Ошибка | Ошибка |

Каждое повторение проверять отдельно: пустое, отсутствующее у явно указанной опции или недопустимое значение считать ошибкой независимо от режима. Последующее корректное значение не исправляет предыдущую ошибку

Пример сравнения, полностью заданного в конфигурационном файле:

```ini
compare = /mnt/storage/first.db
    /mnt/backup/second.db
```

При этих настройках в `precizer.conf` достаточно запуска `precizer` без аргументов. Другой файл с полным набором настроек можно выбрать через `precizer --config=profiles/compare.conf` или `precizer -g profiles/compare.conf`. Для изменения одной из баз изменить соответствующую запись выбранного файла либо передать полный набор параметров отдельным CLI-запуском без `--config`

Примеры записи флагов:

```ini
# Параметры запуска
progress = YES # Показывать прогресс
update = 1
dry-run = false
```

В этом примере `progress` и `update` включаются, а `dry-run` выключается вместе с режимом расчёта контрольных сумм при пробном запуске

Пример нескольких путей и правил фильтрации в файле:

```ini
path = /mnt/storage1
path = /mnt/storage2
ignore = ^cache/
ignore = ^tmp/
include = ^cache/keep/
include = ^tmp/keep/
```

Пример значений `ignore` со строками продолжения:

```ini
ignore = ^cache/
    ^tmp/
    ^something_eles/

ignore = ^other/
    ^things/
```

Эквивалентная запись с повторением ключа:

```ini
ignore = ^cache/
ignore = ^tmp/
ignore = ^something_eles/
ignore = ^other/
ignore = ^things/
```

В обоих случаях в список `ignore` добавляются пять отдельных выражений в указанном порядке. Оба примера сохранить в корневом `precizer.conf` с пояснением их эквивалентности

Пример выбора другого конфигурационного файла:

```sh
precizer --config=profiles/archive.conf
precizer -g profiles/archive.conf
```

Обе команды используют только настройки указанного файла. Например, глубину сканирования следует задавать в нём записью `maxdepth = 2`

## 2 Требования к реализации

1. **Разбор с помощью inih и одна таблица параметров**. Читать файл через `ini_parse_file()` библиотеки inih из `libs/inih` с одним обработчиком записей. Использовать штатный синтаксис библиотеки и параметры из раздела 2.1. Разбор строк, разделителей, комментариев и продолжений поручить inih. Каждую строку продолжения библиотека передаёт отдельным вызовом обработчика с предыдущим ключом. Имена параметров и соответствующие им ключи обработчика брать из существующей таблицы `options[]`: искать точное длинное имя, включая поддерживаемые алиасы. Отдельный словарь параметров для файла не создавать
2. **Один общий обработчик значений**. Использовать существующий `parse_opt()` для CLI и записей конфигурационного файла, сохраняя его `switch` целиком. Обработчик записей inih передаёт ему только ключи разрешённых рабочих опций и их значения. Переиспользовать существующие проверки и связанные действия параметров с учётом правил логических значений из раздела 1; отдельную функцию для каждой опции не создавать. Выбранный источник заполняет один существующий `Config`. Записи `compare` передаются как пути без преобразования логических значений. Для флагов обработчик файла передаёт распознанные логические значения общему обработчику для включения или выключения флага по разделу 1. Общую диагностику ошибок значений, выявленных при разборе, выполнять через небольшую обёртку над `argp_failure()`: сохранять текст CLI, а при чтении файла добавлять префикс с исходным номером текущей строки по пункту 21 раздела 1. Контекст источника нужен для текущего вызова, без хранения происхождения каждого значения. Момент проверки регулярных выражений определён пунктом 12 этого раздела; совместимость `database` с режимом сравнения — пунктом 16 раздела 1. События argp, информационные параметры, служебный `--config`, позиционные аргументы и итоговые проверки остаются в том же обработчике и выполняются при разборе CLI
3. **Два прохода argp с одной таблицей параметров**. Использовать существующую `options[]` для предварительного и основного разбора CLI. Предварительный проход выполнять с `ARGP_SILENT`: сохранять путь из `--config` или `-g`, признак наличия других аргументов и информационного запроса, не применяя рабочие настройки, не проверяя их значения и не выводя сообщений или справки. Аргумент самой опции выбора файла посторонним не считать. Использование `--` отклонять по пункту 26 раздела 1. После успешного прохода при информационном запросе игнорировать выбор файла и перейти к основному разбору CLI. В остальных случаях отклонить сочетание выбора файла с другими аргументами до открытия файла и применения настроек. Затем выбрать источник: явно указанный файл, стандартный файл при исходном `argc == 1` либо только CLI. Для файлового запуска полностью прочитать и применить файл. Основной проход argp сохраняется и в этом случае: в исходном CLI нет рабочих параметров, но его итоговые события проверяют уже заполненный `Config`. Если предварительный argp остановился на ошибке, не разбирать её причину и не сообщать отдельно: отбросить частично найденные результаты, не читать файл и передать исходный CLI обычному обработчику для диагностики; операция не запускается. Такая диагностика имеет приоритет перед проверкой конфликта источников. В основном проходе опция выбора файла повторно распознаётся, но не читает файл и не меняет источник. Значения по умолчанию задавать один раз при инициализации
4. **Проверка итоговых настроек**. Проверять синтаксис и отдельные значения при разборе выбранного источника; для регулярных выражений применять порядок из пункта 12 этого раздела. Наличие обязательных параметров и их взаимосвязи проверять после полного разбора выбранного источника, до начала сканирования или сравнения баз данных. Учитывать исключения для пустого запуска и информационных параметров по пунктам 24 и 25 раздела 1
5. **Разделение настроек и рабочего состояния**. Использовать файл для описания параметров запуска. Управление соединениями с базами данных, скомпилированными регулярными выражениями, состоянием транзакций и другими рабочими ресурсами оставить в программе
6. **Совместимость существующих запусков**. Сохранить существующее поведение запусков только с рабочими CLI-аргументами независимо от наличия и содержимого стандартного файла, с учётом правил для `database`, `compare-filter` и применимости настроек из пунктов 16, 17 и 23 раздела 1. Обеспечить сканирование и сравнение без рабочих CLI-параметров, если автоматически или явно выбранный файл задаёт всё необходимое. Пустой запуск, неполные настройки, информационные параметры и конфликт источников обрабатывать по разделу 1
7. **Общее добавление корней**. Добавить повторяемый параметр `--path=PATH` и его обработку в `parse_opt()`. Для `path` из файла, `--path` и позиционных корней CLI использовать одну обработку добавления пути в `config->roots` с одинаковыми проверками значения. Позиционные аргументы считать корнями только в режиме сканирования. Сохранять порядок обработки существующего argp: порядок смешанных опций и позиционных аргументов может отличаться от их расположения в командной строке. Пустой путь не является допустимым корнем и не означает очистку массива. Записи `path =`, CLI-опции `--path=` и пустые позиционные корни отклонять при обработке значения. Пустой именованный корень отклонять и при сравнении: отсутствие обхода не отменяет проверку значения при разборе
8. **Совместимость database с режимом сравнения**. Сохранить существующую ошибку при совместном указании `database` и режима сравнения. Использовать одну проверку для CLI и файла без отдельной очистки файлового значения
9. **Применение compare-filter**. Накапливать категории выбранного источника в существующем поле `config->compare_filter`. Сохранить существующую проверку, запрещающую фильтр без сравнения, а также проверки обязательного значения опции, допустимых категорий и обязательных путей
10. **Подготовка операндов сравнения**. Пути из записей `compare` и позиционные пути CLI добавлять в существующий массив `db_file_paths`. После полного разбора выбранного источника проверить ровно два элемента. Дальнейшая обработка использует этот массив без отдельных полей для первой и второй баз. Сохранять его существующую инициализацию и освобождение вместе с остальными полями `Config`

11. **Учёт записей файла для пустого запуска**. В локальном контексте разбора хранить признак наличия хотя бы одной записи настройки в файле. Пустые строки, комментарии и заголовки секций его не устанавливают; корректная запись флага устанавливает его независимо от своего логического значения. Не определять наличие записей по итоговым значениям `Config`: они могут совпасть со значениями по умолчанию даже при наличии записей в файле. Использовать этот признак вместе с наличием аргументов CLI для правила пункта 24 раздела 1
12. **Проверка регулярных выражений**. Выражения `ignore`, `include` и `lock-checksum` из файла и CLI сохранять как строки без проверки PCRE2 при разборе. Повторяемые ключи и строки продолжения обрабатывать по обычным правилам накопления. Проверять выражения существующим `compile_patterns()` при подготовке к выполнению операции, без отдельной предварительной компиляции и исключений для режима сравнения. При ошибке выражения завершать запуск до сканирования или сравнения и сохранять обычное сообщение PCRE2: выражение, позиция внутри него и причина, без номера строки конфигурационного файла. Происхождение выражений не хранить. Если после ошибочного выражения при разборе встретится неизвестный ключ или другое недопустимое значение, сообщать об этой ошибке разбора; до компиляции выражений запуск не доходит. Информационные CLI-параметры сохраняют ранний выход без компиляции выражений

Эквивалентные способы передачи нескольких корней в режиме сканирования:

```sh
precizer /mnt/storage1 /mnt/storage2
precizer --path=/mnt/storage1 --path=/mnt/storage2
precizer --path=/mnt/storage1 /mnt/storage2
```

Во всех трёх примерах стандартный файл не читается. Для файлового запуска те же корни задаются в выбранном файле:

```ini
path = /mnt/storage1
path = /mnt/storage2
```

Запускать такую конфигурацию через `precizer` без аргументов, если это стандартный файл, либо через `precizer --config=FILE`. Передача дополнительных корней вместе с `--config` без информационного запроса вызывает конфликт

Выбранный источник формирует массив корней и передаёт его существующему обходу по пункту 22 раздела 1. До отдельного этапа multi-root сохраняются известные ограничения: одинаковые относительные пути разных корней используют общую запись БД, а очистка при `--update` проверяет записи относительно одного корня. Эти ограничения принимаются по пункту 22 раздела 1; полноценная поддержка multi-root относится к отдельному проекту

### 2.1 Настройки inih

Определить параметры библиотеки через `#define` в общем заголовочном файле `src/inih_config.h`, подключаемом приложением и библиотекой перед `ini.h`. Значения параметров не передавать через аргументы компилятора и не дублировать в Makefile

```c
#define INI_MAX_LINE 4096
#define INI_STOP_ON_FIRST_ERROR 1
#define INI_HANDLER_LINENO 1
#define INI_ALLOW_MULTILINE 1
#define INI_ALLOW_INLINE_COMMENTS 1
#define INI_START_COMMENT_PREFIXES "#"
#define INI_INLINE_COMMENT_PREFIXES "#"
#define INI_CALL_HANDLER_ON_NEW_SECTION 1
#define INI_USE_STACK 1
```

- `INI_MAX_LINE=4096` — фиксированный буфер размером 4096 байт. Контроль длины строк поручить inih; при возвращённой библиотекой ошибке завершать запуск без выполнения операции
- `INI_STOP_ON_FIRST_ERROR=1` — прекращать разбор на первой ошибке и завершать запуск
- `INI_HANDLER_LINENO=1` — передавать номер строки обработчику. В сообщениях об ошибках записей использовать номер строки по пункту 21 раздела 1
- `INI_ALLOW_MULTILINE=1` — поддерживать строки продолжения по пункту 13 раздела 1
- `INI_ALLOW_INLINE_COMMENTS=1` — использовать встроенную обработку комментариев после значения по пункту 6 раздела 1
- `INI_START_COMMENT_PREFIXES="#"` — использовать только `#` для комментариев на отдельных строках. Символ `;` сохранять как часть значения
- `INI_INLINE_COMMENT_PREFIXES="#"` — использовать только `#` для комментариев после значения
- `INI_CALL_HANDLER_ON_NEW_SECTION=1` — вызывать обработчик при встрече секции и пропускать её заголовок без изменения настроек
- `INI_USE_STACK=1` — использовать фиксированный буфер на стеке без динамического выделения памяти для него

Остальные параметры inih оставить со штатными значениями по умолчанию

Определения из `src/inih_config.h` должны действовать до первого подключения `ini.h` как в приложении, так и при компиляции реализации inih. Одного подключения заголовка в приложении недостаточно: `ini.c` собирается отдельно. В частности, `INI_HANDLER_LINENO` меняет число аргументов обработчика и должен совпадать у библиотеки и вызывающего кода

### 2.2 Применимость настроек по выбранной операции

Сохранять существующую обработку настроек для выбранной операции, одинаковую для CLI и файла. При сравнении `Config.roots` очищается перед диагностикой; обход файлов, проверка корней и очистка записей БД не выполняются

При сравнении указание `database` вызывает ошибку независимо от источника настроек по пункту 16 раздела 1

Сохранять существующую рабочую компиляцию `ignore`, `include` и `lock-checksum` в обоих режимах. Некорректное выражение вызывает ошибку независимо от источника настроек. Все выделенные ресурсы освобождать обычным завершением `free_config()`

При сравнении сохранять `update`, `dry-run`, `check-level`, фильтры сравнения и настройки вывода. `dry-run=with-checksums` остаётся таким же значением в диагностике, но расчёт сумм не выполняется, поскольку обход файлов пропускается. `progress` не запускает обход при сравнении; связанный признак повторного вывода сохранённых сообщений сохраняет обычное действие

`compare-filter` без включённого сравнения вызывает ошибку. Пустое или недопустимое значение также остаётся ошибкой

Сохранять существующие предупреждения о `--db-drop-inaccessible` без `--update` и `--rehash-locked` без `--lock-checksum` в обоих режимах. Проверки отдельных значений и обязательных путей сохраняются

### 2.3 Чтение записей конфигурационного файла

Чтение конфигурационного файла и обработку его записей разместить в `src/parse_configfile.c`. Общую таблицу параметров и `parse_opt()` сохранить в `src/parse_arguments.c`

Требования описывают завершённый механизм чтения. До первого файлового запуска подготовить общую обработку значений, включая преобразование логических значений и сохранение собственных копий строк. Поддержку каждого аргумента завершать отдельно по порядку раздела 3: необходимые изменения его поведения, документация, тестовые конфигурации и тесты

Диагностику оформлять по пункту 21 раздела 1. Параметры inih применять по разделу 2.1. Использовать `ini_parse_file()` и один обработчик записей inih, непосредственно вызывающий `parse_opt()`. Разбирать и применять записи последовательно, без промежуточного интерфейса обработчиков или преобразования файла в искусственный `argv`

Имя каждой настройки искать точным совпадением в `options[]`, пропуская заголовки групп и записи без длинного имени. Поддерживать существующие длинные алиасы и учитывать характеристики соответствующей основной опции. Не дублировать список имён, ключей и правил проверки значений в отдельной таблице конфигурации. Неизвестные имена и запрещённые файловые ключи отклонять до вызова общего обработчика

Для флагов распознавать логические значения по пункту 12 раздела 1; неподдерживаемое значение отклонять с ошибкой до вызова `parse_opt()`. Учитывать наличие корректной записи по пункту 11 раздела 2 независимо от значения флага. Передавать общему обработчику как истинные, так и ложные значения; значение `with-checksums` у `dry-run` — как аргумент этого параметра. Значения остальных параметров с аргументом передавать в `parse_opt()` для существующих проверок и применения. Для диагностики передавать исходный номер строки только на время текущего вызова, сохраняя стандартную сигнатуру `parse_opt()`. Значения `path` проходят через общую ветвь добавления корней

Передавать открытый файл непосредственно в inih. Штатные правила библиотеки определяют разделители, комментарии, отступы, продолжения и контроль длины строк. Обработчик пропускает заголовки секций и проверяет имена ключей и значения независимо от секции. Для ошибок, обнаруженных при чтении записей, использовать исходный номер строки, переданный библиотекой. Если обработчик уже сообщил причину ошибки, не добавлять общее сообщение о неверном синтаксисе. При ошибке разбора или чтения завершать запуск без выполнения операции

Использовать существующие поля и списки `Config`. Общий обработчик должен сохранять собственные копии строк, поскольку данные, переданные inih, действуют только во время вызова обработчика. Наличие обязательных параметров и совместимость настроек проверять после завершения выбранного источника через итоговые события основного прохода argp

Записи `ignore`, `include` и `lock-checksum`, включая повторы и строки продолжения, сохранять без проверки PCRE2 при чтении файла. Применять существующую рабочую компиляцию и диагностику по пункту 12 раздела 2; отдельная функция предварительной проверки не требуется

Отклонять ключи `help`, `usage`, `version` и `config`. Записи `compare` передавать общему обработчику как пути, без преобразования логических значений. Обрабатывать недоступность файла и ошибки чтения по пункту 19 раздела 1, отличая ошибку чтения от нормального конца файла

### 2.4 Порядок работы программы при запуске

Этот порядок описывает работу подключённого механизма конфигурации. Шаги его внедрения приведены в разделе 3

Организовать последовательность внутри `parse_arguments()`, которая уже вызывается после `init_config()`. Путь выбранной конфигурации хранить в `Config`, а в локальном контексте — признаки других CLI-аргументов, информационного запроса и необходимые признаки разбора. Контекст выбора источника передавать обработчикам argp через `argp_state.input`. Результат чтения файла и признак наличия записей хранить в отдельном локальном контексте, передаваемом обработчику inih через пользовательский указатель. Рабочие значения выбранного источника применяются существующим `parse_opt()`; предварительный проход их не применяет

1. Выполнить предварительный проход argp с той же таблицей, флагами `ARGP_SILENT` и отдельным обработчиком, сохраняющим выбранный путь, признак других аргументов и информационного запроса. Использовать исходный `argv`. Распознавать границы опций и их значений, не применяя настройки и не проверяя значения. Использование `--`, отмеченное библиотекой, считать ошибкой предварительного прохода по пункту 26 раздела 1
2. Если предварительный проход остановился на ошибке, не анализировать и не выводить её отдельно. Отбросить частично найденные результаты, пропустить выбор и чтение файла в пунктах 3–4 и перейти к обычному разбору исходного CLI в пункте 5. Файл в этом случае не читается, операция не запускается
3. После успешного предварительного прохода при информационном запросе сбросить выбранный путь конфигурации и перейти к основному разбору CLI в пункте 5 без проверки конфликта источников и без чтения файла. В остальных случаях проверить конфликт: если указан `--config` или `-g` и есть другие аргументы, завершить запуск с ошибкой до чтения файла и применения настроек. Иначе выбрать только явно указанный файл, только стандартный файл при исходном `argc == 1` либо только CLI. Для CLI-запуска перейти к пункту 5, не обращаясь к стандартному файлу
4. Для файлового запуска полностью прочитать и применить выбранный файл. Отсутствие автоматически выбранного стандартного файла и ошибки открытия или чтения обработать по пункту 19 раздела 1. При ошибке завершить запуск; явно выбранный файл не заменять стандартным
5. Выполнить основной проход argp по исходному CLI. В CLI-запуске `parse_opt()` применяет рабочие опции и обрабатывает информационные запросы. Показ справки и версии остаётся только в этом проходе и последующем обычном выводе программы. В файловом запуске рабочие настройки уже получены из файла, а основной проход встречает только служебные опции выбора файла либо пустой CLI; он нужен для существующих итоговых событий и проверок. Повторное распознавание `--config` или `-g` не читает файл и не меняет источник. При ошибке основного прохода завершить запуск без выполнения операции
6. В итоговых событиях основного прохода проверить настройки выбранного источника с учётом пустого запуска и информационных параметров по пунктам 24 и 25 раздела 1. При сканировании проверить корни, при сравнении — ровно два пути в массиве, заполненном записями файла либо позиционными аргументами CLI. Использовать адаптированный `ARGP_KEY_NO_ARGS` и существующий `ARGP_KEY_END`, с диагностикой отсутствующих обязательных параметров по пункту 9 раздела 1. Сохранить одинаковую для обоих источников проверку совместимости `database` с режимом сравнения в существующем порядке обработки. После успешного разбора и раннего выхода для информационных параметров выполнить существующую нормализацию используемых путей и вывод настроек
7. Освободить временные данные разбора при успешном завершении и при ошибке

## 3 Пошаговая реализация

Выполнять этапы 3.1–3.10 последовательно, сохраняя работоспособность существующих запусков. До первого файлового запуска подготовить общую инфраструктуру, включая обработку логических значений и сохранение строк параметров, и именованный корень `path`. Первым завершить цикл поддержки `path` на этапе 3.8, затем остальных аргументов по одному на этапе 3.9. Изменения режима сравнения выполнять при внедрении соответствующих аргументов

После каждого подготовительного шага и каждого добавленного аргумента выполнить соответствующие проверки, представить пользователю изменения и результаты, затем остановиться. Продолжать только после проверки пользователем и его явного разрешения на следующий шаг. Для аргумента один проверяемый шаг включает код, документацию, тестовые конфигурации и тесты; наличие общего обработчика не заменяет этой проверки

### Цикл добавления одного аргумента

1. Выбрать следующий аргумент и его уникальные сценарии из согласованного плана тестов
2. В одном шаге внести необходимые изменения кода, добавить описание и закомментированный пример в корневой `precizer.conf`, подготовить конфигурационные файлы выбранных тестов и дополнить эти тесты файловыми запусками
3. Выполнить проверки и представить пользователю изменения, использованные сценарии и результаты
4. Остановиться до проверки пользователем и явного разрешения на следующий шаг или аргумент

### Конфигурационный повтор существующего теста

Существующий целевой CLI-запуск сохранить вместе с его аргументами, окружением, подготовленными данными, исходным наличием или отсутствием конфигурационного файла и всеми проверками результата. Сохранение той же команды и golden-шаблона при изменённой подготовке не считается сохранением исходного сценария. Корректировать ожидаемое CLI-поведение только в рамках явно согласованного изменения поведения программы

Непосредственно после исходного CLI-запуска и проверки его результата добавить один запуск той же операции через конфигурационный файл. Файл хранить рядом с golden-шаблонами в `tests/templates/`, используя номер теста и при необходимости номер сценария, например `NNNN_SSS.conf` рядом с `NNNN_SSS.txt`. В файловый запуск передавать только `--config=FILE` либо использовать стандартный файл, если проверяется автоматическое чтение; все рабочие настройки задавать в самом файле

Для всех тестов конфигурации хранить исходное содержимое в нумерованных `.conf`-файлах в `tests/templates/`, копировать нужный файл в рабочую директорию теста и удалять рабочую копию после проверки. Содержимое конфигурации не формировать строками в коде теста. Одинаковый файл разрешается использовать в нескольких сценариях. Проверки отсутствующего файла и каталога вместо файла создают соответствующее состояние файловой системы; проверка корневого документированного `precizer.conf` использует сам этот файл

Проверку игнорирования конфигурации выполнять отдельным дополнительным запуском. Если исходный сценарий выполнялся без конфигурационного файла, сначала выполнить его без файла и проверить результат. Только затем скопировать тестовый `.conf` в рабочую директорию, повторить команду с теми же проверками и удалить рабочую копию. Создание файла до первого запуска подменяет исходный сценарий и запрещено. Общая таблица сценариев и общий golden-шаблон допустимы, но каждый запуск должен пройти собственную проверку результата

Подготовку выполнять один раз существующими CLI-командами. Перед целевым CLI-запуском сохранить подготовленное состояние, которое операция изменяет. После проверки результата CLI восстановить это состояние и выполнить файловый запуск. Например, перед обновлением непустой БД сохранить её копию и восстановить её по тому же рабочему пути перед повтором обновления через файл. Если операция меняет другие данные, способ восстановления определить для конкретного теста. Если исходное состояние не меняется, копирование и восстановление не нужны. Повторно создавать исходную БД или выполнять всю подготовительную последовательность не требуется

Для эквивалентных CLI- и файлового запусков использовать одинаковые проверки результата и статуса завершения. Поле с путём конфигурационного файла является согласованным различием источников: его наличие и значение проверять отдельно, а остальной вывод сопоставлять с тем же существующим полным golden-шаблоном CLI. При CLI-запуске проверять отсутствие этого поля. Отдельную копию шаблона для файлового запуска не создавать. Оба запуска должны начинаться с одинакового состояния и приводить к одинаковому результату

Согласованные различия источников заранее отметить в индивидуальном плане: ошибки, обнаруженные при чтении файла, содержат префикс с исходным номером строки по пункту 21 раздела 1. Такие случаи проверять по полному ожидаемому результату соответствующего источника; ради общего шаблона не удалять сведения об ошибке и не ослаблять сравнение. Ошибочные сценарии с одинаковой диагностикой используют общий golden-шаблон наравне с успешными

Перечни проверок в разделах ниже задают общее покрытие. Распределить их между шагами индивидуального плана, сохраняя по одному файловому повтору каждого уникального сценария. Повторное упоминание проверки в разных разделах не означает добавления ещё одного такого же запуска

Проверить разбор примеров и то, что поставляемый `precizer.conf` содержит закомментированные образцы, обеспечивает обычный успешный показ краткой справки без CLI и не влияет на обычные CLI-запуски

Результат: согласованные сценарии покрыты проверками, документация описывает реализованное поведение, а в корне проекта находится документированный `precizer.conf`

### Сводная карта проверок

Это перечень требуемого покрытия для индивидуального плана, а не дополнительный этап внедрения. Общие механизмы проверять при их подключении, особенности аргументов — в соответствующих шагах. Каждый выбранный в индивидуальном плане существующий CLI-сценарий проверки рабочего аргумента получает один файловый повтор. Новые проверки формата файла, выбора источника и исключительно CLI-поведения планировать отдельно. Повторный прогон существующего теста после изменения общей инфраструктуры не создаёт нового дублирующего сценария

Проверка применения значений: одинаковое применение соответствующих значений через CLI и обработчик inih, поиск основных длинных имён по общей таблице, одиночные и повторяемые значения, порядок записей, все допустимые варианты логических значений и регистр букв, сохранение значения по умолчанию при отсутствии ключа, включение и выключение флагов в обоих порядках с применением последней записи, согласованное изменение связанных настроек прогресса и режимов вывода, переходы между `dry-run = with-checksums`, `dry-run = true` и `dry-run = false`, копирование строк, ошибки формата и запрещённые ключи

Проверка регулярных выражений файла: корректные и ошибочные значения всех трёх параметров, повторяемые ключи и строки продолжения сохраняются в списках без проверки PCRE2 при чтении. Последующие записи продолжают применяться. Некорректное выражение вызывает обычную ошибку при рабочей компиляции без номера строки файла. Если позже при чтении обнаружена неизвестная или недопустимая настройка, сообщать об этой ошибке разбора; компиляция выражений не выполняется

Проверка синтаксиса: значения без кавычек и в одинаковых внешних кавычках обоих видов, сохранение пробелов и обратных слешей внутри, отсутствие подстановок shell, применение логических и числовых значений после снятия кавычек, обычная проверка пустого содержимого и ошибка незакрытых или несовпадающих кавычек с исходным номером строки. Проверить разделители `=` и `:`, строки продолжения с пробелами и табуляцией, комментарии с `#` на отдельной строке и после значения при наличии пробела перед `#`. Проверить сохранение `#` внутри значения без предшествующего пробела и отсутствие комментариев с `;`. Проверить, что оба приведённых примера `ignore` дают одинаковые пять значений в одинаковом порядке. Символы `:` и `;` внутри значения сохраняются, в том числе в строках продолжения. Проверить секции с записями и без них, пустое имя секции `[]`, повторение имён секций и применение одинаковых ключей в разных секциях по общим правилам

Проверка ограничений и ошибок: возврат ошибки inih при переполнении установленного буфера, остановка запуска при ошибке, синтаксически некорректные заголовки секций и правильное указание исходного номера строки в согласованном префиксе. Для одинаковой ошибки значения, выявляемой при разборе CLI и файла, проверить совпадение основного текста сообщения и добавление согласованного префикса только для файла, включая ошибку в строке продолжения. Ошибки PCRE2 сохраняют обычную диагностику без файлового префикса. Новые сообщения проверить по пункту 21 раздела 1

Проверка выбора источника: все случаи таблицы раздела 1, автоматическое чтение только без CLI, выбор стандартного и другого файла через `--config` и `-g`. Проверить формы `--config=FILE`, `--config FILE`, `-g FILE`, `-gFILE`, повторение длинной и короткой форм с чтением только последнего файла. Значение опции выбора файла не считается другим аргументом. Явно выбранный файл не объединяется со стандартным и не заменяется им при ошибке

Проверка конфликтов: без информационного запроса сочетать каждую форму выбора файла с рабочей опцией или позиционным путём. Проверить оба порядка, повторные опции выбора файла и группы коротких опций. Конфликт выявляется до открытия файла и применения настроек. Повторить сценарии с отсутствующим, недоступным и ошибочным выбранным файлом: результатом должен оставаться конфликт, файл не читается. Сообщение должно объяснять необходимость выбрать один источник

Проверка распознавания аргументов: обязательное значение другой опции, похожее на `--config` или `-g`, не выбирает файл. При использовании `--`, отмеченном argp, файл не читать, сообщать `ERROR: Unsupported use of --` и завершаться ошибкой до проверки обязательных путей. Проверить одиночный `--`, разделитель с позиционным путём и сочетания с выбором файла. Значения, которые argp не отмечает таким образом, дополнительно не отклонять; `--config=--` и `--config ./--` позволяют выбрать файл с именем `--`

Проверка независимости CLI: запускать обычные команды без выбора файла при отсутствующем, корректном, недоступном и ошибочном стандартном файле. Оставленные в файле `compare`, `path`, `database`, `update`, флаги и фильтры не меняют операцию, параметры, диагностику и статус завершения CLI-запуска. Недостающие пути не дополняются из файла. Запуск с одним `--` не читает файл и выдаёт ошибку по пункту 26 раздела 1. Подтвердить отсутствие обращений к стандартному файлу

Проверка передачи синтаксических ошибок основному проходу: неизвестная опция до и после выбора файла, отсутствие обязательного значения опции, `--maxdepth=bad --unknown`, `--help --unknown` и `--silent --unknown`. Предварительный проход не выводит сообщений и не применяет настройки; основной получает исходный CLI и сохраняет обычную диагностику. При ошибке предварительного прохода проверка конфликта источников не подменяет обычную диагностику CLI. Ни один файл не открывается, в том числе при повторном распознавании выбора файла основным проходом; операция не запускается

Проверка пустого запуска и обязательных путей: без CLI при отсутствии стандартного файла, пустом файле или файле без записей настроек (только с комментариями, пустыми строками или заголовками секций) выводится краткая справка и возвращается успешный статус. Записи файла без необходимых путей вызывают ошибку, в том числе если все они содержат ложные значения флагов или настройки другой операции. Явно выбранный пустой файл также даёт ошибку отсутствующих путей. При отсутствии корней сканирования проверять подсказку для выбранного источника по пункту 9 раздела 1: ключ `path` для файла, позиционный каталог или `--path` для CLI. Полный набор настроек в стандартном или явно выбранном файле самостоятельно запускает сканирование или сравнение. Попытка дополнить неполный файл через CLI вызывает конфликт. Проверять полный вывод и статус завершения

Проверка информационных параметров: `--help`, `--usage`, `--version` и их короткие формы работают независимо от стандартного и явно указанного файлов, не требуют обязательных путей и не запускают операции. Проверить выбор отсутствующего и ошибочного файла, оба порядка аргументов, группы коротких опций и сочетания с рабочими параметрами: выбор файла игнорируется, вывод совпадает с обычным информационным запуском. Ошибки остальных CLI-аргументов должны сохраняться, включая неизвестную опцию и недопустимое значение после информационного параметра. Отдельно проверить отсутствие дополнительного вывода из предварительного прохода

Проверка регулярных выражений: некорректные выражения из файла и CLI останавливают запуск при рабочей компиляции до выполнения операции, с одинаковой диагностикой PCRE2 без номера строки конфигурации. Обычный `--help` не читает стандартный файл с ошибочным выражением. Команды `--help --ignore="["` и `--help --lock-checksum="["` сохраняют показ справки без проверки CLI-выражений; то же правило действует для `--usage` и `--version`. Корректные `ignore` и `include` работают при сканировании и сравнении, а `lock-checksum` — при сканировании; проверить отдельно файловый и CLI-запуск

Проверка доступности и чтения: без CLI отсутствие стандартного файла допускается, а его недоступность вызывает ошибку. Отсутствие или недоступность явно выбранного файла и ошибка чтения используемого файла завершают запуск. Проверить остановку и после чтения части настроек, без выполнения операции. При обычном CLI-запуске, информационном запросе и конфликте источников никакой конфигурационный файл не проверяется и не читается

Проверка корней: повторить CLI-сценарии этапа 3.5 после подключения выбора источника. Проверить накопление файловых `path` в порядке записей. Для обоих источников проверить отсутствие обязательных корней, нормализацию и сохранение повторяющихся элементов

Проверка сравнения: сохранить CLI-сценарии позиционных путей. Файловый список из двух записей `compare` должен работать без CLI либо с выбором файла. Проверить эквивалентность повторных ключей и строк продолжения, порядок элементов, ошибки количества путей и пустого значения. Значение с пробелами остаётся одним путём; слова `true` и `false` остаются именами файлов. Стандартный файл со списком сравнения не должен мешать обычному CLI-запуску

Проверка применимости настроек: при сравнении корни из файлового `path` либо CLI `--path` не проверяются на доступность и не обходятся. Указание `database` при сравнении вызывает ошибку в обоих источниках. Не требовать скрытия остальных настроек из диагностики или их сброса к значениям по умолчанию

Проверка сохраняемых настроек: сравнение продолжает учитывать `ignore`, `include`, `check-level`, `update`, `dry-run` и настройки вывода. Сохранить сценарии обновления старых БД при сравнении. Проверить файловый повтор сравнения с `dry-run=with-checksums` по тому же полному шаблону, что и CLI с этим значением. Сохранить существующую обработку настроек обхода и предупреждения об их зависимостях

Проверка `database`: совместное указание с режимом сравнения вызывает ошибку в CLI и файле независимо от порядка параметров. Отсутствие настройки не мешает сравнению. При сканировании применяется значение выбранного источника, при повторении — последнее

Проверка `compare-filter`: все случаи таблицы раздела 1 отдельно для файла и CLI, накопление категорий внутри источника, повторы одинаковых значений и остановка на пустом или недопустимом значении. Без включённого сравнения проверить ошибку независимо от допустимости значения фильтра. Сохранить требования к корням и двум операндам сравнения

### Проверка каждого этапа

После каждого согласованного шага, изменяющего код или тесты, запускать полный `make tests-debug`, включая медленные сценарии. Эквивалентные CLI- и файловые запуски проверять по одному существующему полному шаблону с отдельной проверкой поля пути конфигурации; отдельные шаблоны использовать для новых сценариев и согласованных различий между источниками по пункту 21 раздела 1. Файловые сценарии выполнять в изолированных рабочих директориях с существующими тестовыми помощниками и восстановлением подготовленного состояния по индивидуальному плану. Проверки выбора источника, независимости CLI и конфликта до чтения файла относятся к общей инфраструктуре и не дублируются для каждого аргумента. После проверки остановиться и передать результат пользователю; успешные тесты сами по себе не разрешают следующий шаг
