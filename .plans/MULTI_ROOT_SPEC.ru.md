# Техническое задание: восстановление поддержки нескольких корней обхода

Статус: проект для согласования, реализация не разрешена

Документ определяет требования к восстановлению multi-root в precizer. Все предложенные правила, включая изменение набора корней, сравнение БД и ограничения миграции, подлежат согласованию до изменения исходного кода

**1. Цель и границы работы**

Программа должна надёжно создавать и обновлять одну базу данных по нескольким корневым каталогам. Каждый файл должен однозначно принадлежать своему корню независимо от порядка аргументов PATH, порядка обхода и числовых ID других корней

Работа охватывает схему БД, миграцию, сопоставление корней, чтение и сохранение файловых записей, промежуточное сохранение SHA512, очистку, сравнение БД, диагностический вывод, тесты и документацию

Алгоритм SHA512, условия определения изменения файла и действующие правила следования символическим ссылкам сохраняются. Автоматическое распознавание переименованных каталогов, сопоставление разных корней по содержимому и новый интерфейс ручного сопоставления корней в эту работу не входят

**2. Исходное состояние**

Обход уже выполняется отдельно для каждого элемента `config->roots`, однако действующая таблица `files` содержит уникальный `relative_path` без ссылки на корень. Поиск файловой записи не учитывает корень, а очистка проверяет все записи относительно одного пути, полученного через `LIMIT 1`

В коммите `85a7733` от 12 марта 2024 года сохранены отключённые фрагменты с `path_prefix_index` и составной уникальностью. Эти фрагменты добавлены в доступную историю уже под `#if 0`; они содержат несовместимые с текущим кодом имена функций, столбцов и SQL-параметров. Они используются как материал для анализа, а не как готовая реализация для механического включения

**3. Термины и обязательные инварианты**

| Термин | Определение |
|---|---|
| Корень | Строка PATH после действующей нормализации завершающих `/` |
| ID корня | Значение `paths.ID` в конкретной БД |
| Относительный путь | Путь файла внутри соответствующего корня |
| Идентичность файла | Пара `(ID корня, относительный путь)` внутри одной БД |
| Набор корней | Уникальные строки корней без учёта порядка аргументов |

Обязательные инварианты:

- Каждая файловая запись принадлежит ровно одному существующему корню
- Одинаковый относительный путь допускается в разных корнях и не допускается повторно внутри одного корня
- ID корня определяется по строке пути, а не по позиции аргумента, порядку строк SQL, величине ID или порядку обхода
- Повторный запуск с тем же набором корней сохраняет их ID и принадлежность файлов
- Неизменившиеся файловые записи сохраняют свои `files.ID`
- Ни обновление, ни очистка, ни возобновление хеширования не могут использовать состояние одноимённого файла из другого корня
- Числовые ID разных БД не используются для установления соответствия между корнями этих БД

Пример: если `/data/A` имеет ID `7`, а `/data/B` — ID `42`, оба запуска `precizer /data/A /data/B` и `precizer /data/B /data/A` должны находить `same.txt` по парам `(7, same.txt)` и `(42, same.txt)` соответственно

**4. Правила строкового сопоставления PATH**

Сравнение выполняется по полной нормализованной строке с учётом регистра. Не применяются `realpath()`, сравнение по началу строки, имени последнего каталога, inode, устройству или содержимому файлов. Unicode-нормализация и приведение регистра не выполняются

Предлагаемые правила:

| Входные пути | Результат |
|---|---|
| `data` и `data/` | Один корень после действующей нормализации |
| Повтор одного корня в аргументах | Один обход и один вклад в статистику; сохраняется позиция первого появления |
| `data` и `./data` | Разные корни |
| `data/sub` и `data//sub`, либо `data` и `x/../data` | Разные строки корней; внутренние разделители и компоненты не нормализуются |
| Относительный и абсолютный путь к одному каталогу | Разные корни |
| `data` и `data/subdir` | Самостоятельные корни |
| Разные строковые пути к одному физическому каталогу | Самостоятельные корни в рамках действующих правил обхода |

Для вложенных или физически совпадающих корней файл может учитываться несколько раз, но в разных пространствах относительных путей. Дедупликация по физическому файлу не выполняется

Корень `/` при удалении завершающих разделителей остаётся `/`. Пустой PATH не становится допустимым корнем

Относительные PATH продолжают разрешаться относительно текущего рабочего каталога процесса. Одна и та же строка относительного PATH из другого рабочего каталога не позволяет обнаружить смену физического источника; автоматическое обнаружение такого случая не входит в задачу. Это ограничение должно быть явно отражено в документации

**5. Требования к схеме БД**

Версия схемы повышается с `4` до `5`

| Объект | Требование |
|---|---|
| `paths.ID` | Устойчивый идентификатор корня |
| `paths.prefix` | Непустая уникальная строка корня |
| `files.ID` | Существующий самостоятельный идентификатор файловой записи |
| `files.path_prefix_index` | Обязательный ID существующего корня |
| `files.relative_path` | Обязательный относительный путь, без глобальной уникальности |
| Уникальность файла | `UNIQUE(path_prefix_index, relative_path)` |

Ограничение и индекс, обеспечивающие глобальную уникальность `relative_path`, заменяются составной уникальностью. Поиск по корню и относительному пути должен использовать индекс; полный просмотр всех файлов для каждого поиска недопустим

Удаление корня не должно оставлять файловые записи без владельца. Повторное использование SQLite числового ID после удаления строки не должно приводить к перепривязке сохранившихся файлов к новому корню. Способ обеспечения ссылочной целостности должен быть единым для создания, миграции и изменения состава корней

**6. Миграция старых БД**

Перед миграциями проверяется возможность однозначно определить владельца существующих файлов

| Состояние старой БД | Требуемое поведение |
|---|---|
| Есть файлы и ровно один корректный корень | Все файлы связываются с фактическим ID этого корня |
| Нет файлов | Миграция допустима независимо от количества корректных сохранённых корней; существующие корни сохраняются |
| Есть файлы и несколько корней | Автоматическая миграция отклоняется без изменения БД |
| Есть файлы, но нет корректного корня | БД признаётся непригодной для однозначной миграции; изменения не выполняются |

При переходе `4 → 5` сохраняются `paths.ID`, `files.ID`, `offset`, `sha512`, `stat` и `mdContext`. ID единственного корня может отличаться от `1`

Проверяются все сохранённые корни, а не только строки, признанные корректными. Корректный `prefix` представляет собой непустую строку без встроенного NUL, соответствующую действующей нормализации завершающих `/`. Существование или доступность каталога на момент миграции не является условием корректности строки. Некорректные строки, включая пустой `prefix`, не исправляются догадкой и приводят к отказу до изменений даже при пустой таблице файлов

Перестроение таблицы, создание индексов и запись версии `5` выполняются в одной транзакции. Ошибка или обработанное прерывание до фиксации этой транзакции возвращают БД к состоянию до перехода `4 → 5`. Недопустимы сочетания новой схемы со старой версией и старой схемы с новой версией

Для версий `0–3` сохраняются необходимые действующие преобразования старых форматов, после которых выполняется переход к версии `5`. Проверка неоднозначности владельца файлов должна предшествовать изменениям старой БД. Требование побайтового сохранения `stat` относится к переходу `4 → 5`, поскольку более ранние версии требуют преобразования этого поля

Миграция физической БД требует `--update`. При отказе выводится причина, включая отсутствие исходной привязки файлов к корням, если именно это препятствует обновлению. Выбор первого корня, распределение по наличию файлов на диске и назначение корней по порядку аргументов запрещены

**7. Изменение набора корней и режим `--force`**

Ниже приведена предлагаемая политика для существующей БД. Все проверки возможности операции выполняются до изменения состава корней и связанных файлов

| Ситуация | Условие | Результат |
|---|---|---|
| Тот же набор, другой порядок | Дополнительные флаги не требуются | ID и принадлежность записей сохраняются |
| Добавлены корни, все прежние сохранены | `--update` | Новые корни получают собственные ID и пустую историю файлов |
| Добавлены корни без `--update` | Включая одиночный `--force` | Отказ без изменения состава корней и файлов |
| Исключена часть корней, новые не добавлены | `--update --force` | Удаляются только исключённые корни и принадлежащие им записи |
| Исключение корней без необходимых флагов | Любой порядок аргументов | Отказ без изменения состава корней и файлов |
| В БД один корень, передан один другой корень | `--update --force` | Однокорневый перенос: меняется строка корня с сохранением его ID и файловых записей |
| В multi-root одновременно исключены старые и добавлены новые корни | Включая `--update --force` | Отказ из-за отсутствия однозначного соответствия |
| Отсутствуют PATH | Любые флаги | Сохраняется отказ для режима сканирования |

При создании новой БД принимается весь набор уникальных корней по действующим правилам выбора режима создания. Существующее требование наличия БД для режима `--update` сохраняется

Однокорневый перенос является сохранением существующего сценария. Он не распространяется на ситуацию «один несовпавший старый и один несовпавший новый корень» внутри multi-root. После переноса необходимость повторного хеширования определяется действующими правилами проверки файлов

Удаление нескольких исключённых корней и их файлов выполняется атомарно. Сохраняемые корни не перенумеровываются. Если среди удаляемых записей есть путь, защищённый действующим `--lock-checksum`, вся операция изменения набора корней отклоняется с перечислением причины; `--force` не снимает защиту контрольных сумм

Отсутствие PATH среди аргументов и недоступность переданного PATH на файловой системе являются разными событиями. Недоступность сама по себе не разрешает удалять корень из БД

**8. Обход, запись и продолжение хеширования**

Перед обработкой файлов очередного корня его ID определяется по `paths.prefix` и сохраняется в контексте обработки. Поиск ID выполняется один раз на корень в проходе обработки содержимого, а не для каждого файла. Проход сбора статистики не требует сохранённых файловых записей

Каждый объект `File` должен содержать принадлежность корню до первого обращения к БД. Это требуется и для нового файла, и для уже существующей записи

Все чтения по имени используют пару `(path_prefix_index, relative_path)`. Вставка записывает оба значения. Дальнейшие обновления по `files.ID` допустимы после получения этого ID в правильном контексте корня

Промежуточные сохранения SHA512, штатное завершение, обработка прерывания и повторный запуск используют ту же принадлежность. Перестановка корней между прерванным и повторным запуском не меняет источник сохранённого offset или контекста хеширования

Пакетные транзакции и существующий интервал сохранения сохраняются. Изменение порядка корней может менять порядок вывода и момент обработки файла, но не итоговое соответствие файлов, корней и контрольных сумм

**9. Очистка, недоступность и фильтры**

Очистка обрабатывает файловые записи отдельно для каждого корня и проверяет их относительно соответствующего открытого каталога. Получение единственного корня через `LIMIT 1` для всей БД недопустимо

Если после предварительной проверки корень недоступен при обходе или очистке, его файловые записи сохраняются, предупреждение содержит этот корень, обработка остальных корней продолжается. `--db-drop-inaccessible` не разрешает массовое удаление записей из-за невозможности открыть сам корень

Предварительная проверка корректности входных PATH сохраняет существующее поведение: некорректный или отсутствующий каталог, обнаруженный на этой стадии, может остановить запуск до обхода. Расширение предварительной проверки до режима частичного принятия недоступных PATH в данную работу не входит. Проверки продолжения после недоступного корня должны отдельно покрывать отказ открытия после успешной предварительной проверки

Фильтры `--ignore`, `--include` и `--lock-checksum` продолжают сопоставляться с относительным путём внутри каждого корня. Одинаковый шаблон действует во всех корнях. Новый синтаксис фильтрации по корню не вводится

Правила `--db-drop-ignored`, `--db-drop-inaccessible` и защиты отсутствующих либо недоступных checksum-locked файлов сохраняются внутри каждого корня. Удаление файла в одном корне не затрагивает одноимённые записи в другом

**10. Режим `--dry-run`**

Физическая БД, её версия, строки корней, файловые записи и сохранённые состояния SHA512 остаются неизменными. Это требование действует также при сочетаниях `--dry-run --update` и `--dry-run --update --force`

Проверки допустимости операций совпадают с обычным запуском. Для нового корня используется отдельное состояние без сохранённой истории, а для допустимого однокорневого переноса — виртуальное соответствие существующему корню. Виртуальные идентификаторы не записываются в физическую БД и не должны совпадать с чужой файловой историей

Для старой схемы в рамках этой задачи предлагается ограниченное поведение: запуск останавливается до сканирования и сообщает, что требуется реальная миграция с `--update` без `--dry-run`. Симуляция миграции старых схем не входит в объём реализации. Нельзя считать пропущенную миграцию выполненной и затем обращаться к отсутствующим столбцам

При отсутствии физической БД сохраняется действующий сценарий симуляции с временной БД в памяти, созданной по новой схеме. Порядок принятия флагов создания и обновления остаётся действующим

**11. Сравнение БД**

Предлагаются следующие правила после проверки совместимости схем обеих БД:

| Состав БД | Правило соответствия файлов |
|---|---|
| В каждой БД ровно один корень | Сравнение по относительному пути независимо от различий строк корней, как в существующем режиме |
| Все остальные случаи, включая несколько корней или пустую БД без корней | Сравнение по паре `(строка корня, относительный путь)` |

В multi-root ID корней используются только для соединений внутри соответствующей БД. Между БД сопоставляются полные строки `paths.prefix`; разные ID и порядок создания корней не влияют на результат

Если строка корня присутствует только в одной БД, её файлы относятся к существующей категории файлов, отсутствующих во второй БД. Различие наборов корней само по себе не является технической ошибкой. У пустого корня нет собственных файловых различий; отдельное сравнение состава пустых каталогов не вводится

Выбор правила сравнения учитывает все сохранённые корни, включая пустые. Поэтому добавление второго пустого корня переводит сравнение из однокорневого в multi-root. Например, равенство файлов из одиночных корней `A` и `B` не сохраняется автоматически после добавления корня `C` в первую БД: строки `A` и `B` уже не соответствуют друг другу по правилу multi-root. Это явное ограничение совместимости предложенной политики

Сравнение checksum выполняется только для соответствующих файлов. Одинаковые относительные имена в несопоставленных корнях не сравниваются друг с другом. Для multi-root с разными путями монтирования автоматическое сопоставление не выполняется; это ограничение отражается в документации

`--compare-filter`, `--ignore` и `--include` сохраняют назначение. Регулярные выражения продолжают применяться к относительному пути, а вывод multi-root дополнительно указывает строку корня

**12. Диагностический вывод и документация**

Для каждого сообщения о файле в multi-root должна однозначно определяться пара «корень, относительный путь». Заголовок текущего корня обновляется при переходе к следующему корню. Сообщения, выводимые позднее из истории предупреждений, содержат собственное указание корня и не зависят от ранее напечатанного заголовка

В `--silent` те сообщения, которые по действующим правилам остаются видимыми, также должны сохранять однозначность. Для списков различий multi-root корень и относительный путь выводятся отдельными различимыми полями с однозначным экранированием специальных символов. Разные пары не должны становиться неразличимыми после простого склеивания строк

Формат вывода для одного корня сохраняется там, где изменение не требуется для сообщения о новой версии схемы или новой ошибке. Конкретный формат новых строк закрепляется полными golden-шаблонами

Справка и README описывают несколько PATH, независимость от порядка, строковую идентичность, повторяющиеся и вложенные корни, ограничения относительных PATH, правила `--force`, `--compare`, миграции и `--dry-run`. `README.ru.md` обновляется первым как оригинал; `README.md` содержит соответствующий перевод на US English. Документация функций оформляется в `.c` в стиле Doxygen

**13. Критерии приёмки**

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| MR-01 | Два корня содержат `same.txt` с разным содержимым | Две записи с правильными корнями и независимо проверенными SHA512 |
| MR-02 | Повторный запуск с обратным порядком корней | Неизменные ID корней, ID файлов и контрольные суммы; нет лишнего хеширования неизменённых файлов |
| MR-03 | Изменён файл только в первом корне | Обновляется только его запись |
| MR-04 | Удалён файл только в первом корне | Очистка не удаляет одноимённую запись второго корня |
| MR-05 | Повтор одного PATH и его варианта с завершающим `/` | Один корень, один обход и однократная статистика |
| MR-06 | `data`, `./data`, абсолютный и вложенный корни | Принадлежность соответствует строковым правилам; физические совпадения не смешивают записи |
| MR-07 | Корень недоступен при обработке после предварительной проверки | Его записи сохраняются, доступные корни обрабатываются; проверяется также `--db-drop-inaccessible` |
| MR-08 | Добавление, исключение и смешанная замена корней | Все строки таблицы раздела 7 соблюдаются, сохраняемые ID не меняются |
| MR-09 | Однокорневый `--update --force` | ID корня и файлов сохраняются; контрольные суммы переиспользуются по действующим правилам |
| MR-10 | Исключаемый корень содержит checksum-locked запись | Изменение состава корней отклоняется целиком; данные сохраняются |
| MR-11 | Прерывание и возобновление с обратным порядком корней | Состояние SHA512 относится только к своему корню; итоговые checksum совпадают с независимым расчётом |
| MR-12 | Миграция v4 с единственным корнем, ID которого не равен `1` | Сохранены фактический ID корня, ID файлов и все поля файловых записей |
| MR-13 | Старая непустая БД с несколькими корнями либо без корня | Отказ до изменений; версия и содержимое физической БД не меняются |
| MR-14 | Ошибка SQL либо обработанное прерывание во время `4 → 5` | Откат схемы, индексов, файловых данных и версии этого этапа |
| MR-15 | Пустые БД и поддерживаемые версии `0–3` | Определённая миграция без выдуманной принадлежности файлов; сохранены необходимые старые преобразования |
| MR-16 | `--dry-run` на v5, включая новые корни, удаление и перенос | Допустимость и предполагаемые действия соответствуют обычному режиму; физическая БД побайтово неизменна |
| MR-17 | `--dry-run` на старой схеме | Понятное сообщение о необходимой миграции; нет сканирования, записи и запросов отсутствующих столбцов |
| MR-18 | Сравнение двух однокорневых БД с разными строками корней | Сохраняется существующее сравнение по относительным путям |
| MR-19 | Сравнение multi-root с разными локальными ID и порядком корней | Результат определяется строками корней и относительными путями |
| MR-20 | В сравнении корень присутствует только с одной стороны | Его файлы попадают в правильную категорию отсутствующих; чужие checksum не сравниваются |
| MR-21 | Фильтры, checksum-lock, обычные и отложенные сообщения | Сохранены правила фильтрации и защиты; все видимые сообщения multi-root однозначны |
| MR-22 | Корни с пробелами, кавычками, UTF-8 и сходными префиксами | Корректное параметризованное сравнение полных строк и различимый вывод |
| MR-23 | Сравнение с пустыми корнями и БД без корней | Правило выбирается по полному составу корней; результат соответствует описанному переходу между однокорневым и multi-root сравнением |

Новые тестовые помощники проверяют файловые записи по корню и относительному пути. Проверки только по `relative_path` недостаточны для подтверждения multi-root. Для контрольных сумм используются независимые ожидаемые значения, а для неизменности данных — проверки ID и значимых полей, дополненные побайтовой проверкой БД в сценариях без записи

Итоговая команда проверки: `make tests-debug`, один полный запуск с медленными сценариями. Он выбран из-за проверок промежуточного сохранения и возобновления SHA512. Последовательный запуск нескольких вариантов тестов по умолчанию не требуется

При неудаче сборки или тестов дальнейшие изменения останавливаются согласно AGENTS.md; причина и предлагаемые решения выносятся на согласование
