## Правила выполнения

Каждый выбранный целевой CLI-запуск получает ровно один файловый повтор после проверки результата CLI. Подготовительные команды остаются CLI и выполняются один раз. Все рабочие параметры повторяемого запуска находятся в файле; в CLI остаётся только выбор файла. Сценарии автоматического чтения проверяются отдельно

Конфигурации хранятся в `tests/templates/` рядом с шаблонами вывода. В таблицах ниже пути `.conf` и `.txt` указаны относительно этой директории. Наличие имени в плане означает будущий файл, если прямо не сказано, что шаблон уже существует. Один существующий golden используется для обоих эквивалентных запусков; совпадение номера конфигурации и шаблона не требует копировать одинаковый golden

В таблицах `D1` означает `tests/fixtures/diffs/diff1`, `D2` — `tests/fixtures/diffs/diff2`, `D` — `tests/fixtures/diffs`. Это сокращения только для документа. В конфигурации записываются реальные значения. Имена функций и существующих golden однозначно определяют целевой запуск, даже если номера строк исходника изменятся

Ожидаемые коды завершения приводятся как в существующих тестах: `COMPLETED` — 0, `FAILURE` — 1, `WARNING` — 32. Статус самого тестового помощника `SUCCESS` не является кодом приложения

Для восстановления состояния применяются следующие правила:

- **Создание**: до обоих запусков БД отсутствует. После проверки CLI удалить только созданную им БД, затем выполнить файловый запуск. Исходные файлы не пересоздавать. Если БД нужна следующему тесту, оставить результат файлового запуска
- **Обновление**: сохранить подготовленную БД непосредственно перед целевым CLI-запуском и восстановить её под тем же именем перед файловым повтором. Изменение содержимого файлов, временных меток и прав доступа не повторять
- **Чтение или dry-run**: использовать то же состояние без копирования, если целевая операция его не меняет. Сравнение с `update` относится к изменяющим операциям: восстанавливать обновляемые входные БД
- Сохранять одинаковые окружение, права доступа и тестовые воздействия до завершения обеих половин пары. Снимки и рабочие конфигурации размещать вне сканируемых корней. Проверки содержимого БД, уже входящие в цель теста, повторять после файлового запуска

Подстановки `$TMPDIR` и `$DBNAME` в существующих командах выполняет тестовый запуск CLI. Для соответствующего файлового повтора тест подготавливает рабочую копию `.conf` с фактическими значениями. Это не добавляет подстановку переменных в приложение. В файл переносится само значение пути или регулярного выражения, без оболочечных кавычек и дополнительного экранирования C-строки

Файловые ошибки значений получают путь и строку, поэтому для них нужны отдельные полные ожидаемые сообщения. Основной текст ошибки сохраняется по требованиям основного плана. Для runtime-ошибок после разбора, например отсутствующей БД, общий golden сохраняется. Не удалять части вывода ради совпадения. При дополнении выбранного теста учитывать оба потока вывода: многие нынешние проверки сравнивают stdout, лишь разрешая stderr

## Порядок внедрения аргументов

Подготовительные этапы 3.2–3.7 основного плана выполняются до первого рабочего файлового запуска. Общая обработка логических значений и сохранение строк параметров должны быть проверены уже на этапе 3.6. Регулярные выражения из обоих источников проверяются существующей рабочей компиляцией, без предварительной проверки при чтении файла. Наличие общих механизмов не означает завершённой пользовательской проверки каждого распознаваемого аргумента

### Что не дублируется

Подготовительные создания БД в update/compare-тестах не получают файловых повторов. Из `0009` не повторяются остальные варианты деревьев и очистки, уже использующие проверенные параметры; из `0030` — остальные сочетания повреждений, прав и блокировок. Это сохраняет существующее алгоритмическое покрытие без повторной проверки того же способа передачи аргумента

Составные шаблоны `0011_001.txt`, `0011_002_3.txt`, `0016_001_1.txt`, `0016_001_2.txt`, `0024_003.txt` описывают несколько запусков подряд. Их не использовать для одиночного файлового повтора и не повторять ради них подготовительную цепочку. Выбраны самостоятельные цели с собственными полными шаблонами

Короткие CLI-имена, расположение CLI-опции до/после позиционных операндов, окружение терминала, работа журнала, прерывания и SQL-ошибки сохраняют собственные проверки. Они не требуют нового `.conf` при каждом упоминании уже проверенного параметра

## Ограничения исполнения и приёмка

`test0028_6` и набор `test0030` помечены `SLOWTEST`. При проверке шагов compare-filter и rehash-locked выбранные цели должны действительно выполняться; запуск с пропуском медленных тестов их не проверяет. Новые проверки формата, выбора источника и очистки состояния не относить к медленным. Команду проверки выбирать по действующим правилам репозитория с учётом нужного покрытия

`test0028_11()` содержит требование отдельного явного разрешения перед изменением и повторной построчной проверки человеком. Согласование этого плана не заменяет такого разрешения на будущую правку. Защищённые `prepare()` и `test0036()` для выбранного подхода менять не требуется: тестовые конфигурации подготавливаются в соответствующих сценариях существующими помощниками

Перед завершением каждого шага проверить, что у выбранной цели один файловый повтор, подготовка не повторяется, восстановлено нужное исходное состояние, совпадают результат и ожидаемый код, а используемый golden проверяет полный предусмотренный вывод. Если выявлена новая концептуальная зависимость или противоречие, согласовать изменение поведения и отразить его в основном плане.
