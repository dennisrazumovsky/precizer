# План изменений для поддержки конфигурационного файла

Документ задаёт согласованные требования и порядок реализации поддержки конфигурационного файла

Поддержка конфигурационного файла позволяет хранить параметры повторяющихся запусков precizer в файле и переопределять отдельные значения аргументами командной строки

## 1 Согласованные требования

1. **Охват параметров**. Все параметры, которые сейчас передаются через командную строку, должны поддерживаться в конфигурационном файле, кроме информационных параметров `help`, `usage`, `version` и служебного параметра `config`. Эти четыре параметра доступны только в CLI. Корни сканирования, режим сравнения и пути к обеим сравниваемым базам поддерживаются в конфигурационном файле
2. **Порядок разбора и приоритет CLI**. После инициализации значениями по умолчанию сначала полностью разбираются и применяются записи конфигурационного файла в порядке их появления, затем параметры CLI. Этот порядок действует во всех режимах при успешном предварительном проходе. При синтаксической ошибке предварительного прохода файл не читать, а диагностику поручить основному разбору CLI по пункту 3 раздела 2. Для одиночных значений вроде `maxdepth` и `database` действует последнее прочитанное значение, поэтому явно переданное значение CLI заменяет значение из файла. Флаги, включая `dry-run`, обрабатываются по правилам пункта 12. Отсутствие параметра в CLI сохраняет значение из файла, кроме `database` в режиме сравнения по пункту 16 и настроек, неприменимых к выбранной операции, по пункту 23
3. **Автоматическое обнаружение и относительные пути**. Имя конфигурационного файла формируется из `APP_NAME` и суффикса `.conf`: для precizer это `precizer.conf`. Если файл не выбран явно через CLI, он ищется в текущей рабочей директории и автоматически используется при его наличии. Относительные пути из файла разрешаются относительно рабочей директории запуска, как пути из CLI, в том числе при расположении конфигурационного файла в другой директории
4. **Отключение и сброс настроек через CLI**. Отдельные средства отключения настроек конфигурационного файла через CLI не предусматриваются. В CLI не добавляются новые отрицательные флаги, формы передачи `false` для отключения флагов, параметры сброса к значениям по умолчанию и очистки списков. Приоритет CLI действует в рамках значений и действий, доступных через поддерживаемые параметры командной строки
5. **Пути в конфигурационном файле**. Для корней сканирования используется повторяемый параметр `path`. Каждая строка со значением содержит один путь, а несколько таких строк задают список корней сканирования
6. **Формат без секций**. Новая запись конфигурационного файла начинается со строки вида `ключ = значение`. Разделителем ключа и значения служит только `=`; форма `ключ:значение` недопустима. Строки продолжения оформляются по правилам пункта 13. Комментарий начинается с `#` и продолжается до конца строки. Символ `;` не начинает комментарий. Секции не используются
7. **Повторяемые ключи**. Один и тот же ключ может встречаться в файле несколько раз. Для `path`, `ignore`, `include` и других параметров, поддерживающих несколько значений, каждая запись добавляет отдельное значение в список. Значения из CLI дополняют список после значений из файла. Корни из `path` в файле можно дополнить через `--path` и позиционные корни CLI по пункту 15
8. **Явный выбор конфигурационного файла**. Параметр `--config=FILE` доступен только в CLI и задаёт путь к конфигурационному файлу, который используется вместо файла по умолчанию. Ключ `config` внутри конфигурационного файла не поддерживается. Относительный путь в `--config` разрешается относительно текущей рабочей директории
9. **Обязательные параметры**. Для выполнения сканирования требуется хотя бы один корень, для сравнения — пути к двум базам по пункту 10. Проверять их наличие после полного разбора конфигурационного файла и CLI: файл может задавать всё необходимое либо дополняться аргументами CLI. Если обязательных путей недостаточно, формировать ошибку с тем же текстом и оформлением, что и в аналогичном запуске только с CLI. Исключения для пустого запуска и информационных параметров определены в пунктах 24 и 25
10. **Сравнение баз данных**. Режим сравнения включать через `compare = true` в конфигурационном файле или `--compare` в CLI. К `compare` в файле применять общие правила флагов из пункта 12. Пути к базам задавать одним из двух взаимоисключающих способов: оба именованных параметра `compare-first` и `compare-second` по пункту 18 либо ровно два позиционных аргумента CLI в порядке «первая база, вторая база», как в `precizer --compare FIRST_DB SECOND_DB`. При включённом сравнении наличие хотя бы одного именованного пути из файла или CLI вместе хотя бы с одним позиционным путём считать ошибкой. Неполная именованная пара и количество позиционных путей, отличное от двух при отсутствии именованных, также являются ошибками. Проверять это после полного разбора файла и CLI независимо от источника включения режима. Параметры `path` и `--path` не используются для передачи сравниваемых баз данных. Если стандартный файл задаёт режим и оба именованных пути, запуск `precizer` без аргументов CLI должен выполнять сравнение. Если файл задаёт только режим сравнения, оба пути можно передать позиционно через CLI
11. **Имена ключей**. Использовать длинные имена параметров CLI без начальных `--`, сохраняя дефисы: например, `maxdepth`, `one-file-system`, `dry-run`
12. **Логические значения флагов**. В конфигурационном файле принимать `true`, `yes`, `on`, `t`, `y`, `1` как логическую истину и `false`, `no`, `off`, `f`, `n`, `0` как логическую ложь. Регистр букв не учитывать, пробелы вокруг значения игнорировать. Истинное значение вызывает то же действие, что и соответствующий CLI-флаг без аргумента. Запись с ложным значением пропускается: она не меняет состояние флага и связанных настроек, заданное значениями по умолчанию или предыдущими записями. Например, после `progress = true` запись `progress = false` оставляет флаг включённым. Для `dry-run` дополнительно поддерживать значение `with-checksums` с тем же действием, что и `--dry-run=with-checksums`
13. **Строки продолжения**. Поддерживать запись дополнительных значений на следующих строках с отступом из пробелов или табуляции. Строки с ключом начинать без отступа. Каждую строку продолжения обрабатывать как повтор предыдущего ключа с отдельным значением, применяя существующие правила этого параметра. Для `ignore`, `include`, `path` и других параметров со списком каждая такая строка добавляет отдельный элемент. Пустые строки и комментарии значений не добавляют
14. **Документированный файл по умолчанию**. Добавить `precizer.conf` в корень проекта. Сохранить в нём приведённые в этом документе примеры, включая строки продолжения и эквивалентную запись с повторением ключа. Для каждой поддерживаемой настройки привести пример, назначение, допустимые значения, поведение по умолчанию и существенные условия применения. Источниками пояснений служат `README.ru.md`, `README.md` и описания параметров для `--help` в `src/parse_arguments.c`. Примеры настроек поставлять закомментированными с помощью `#`, чтобы они не применялись при автоматическом чтении файла. Параметры, доступные только в CLI, описать в комментариях с примерами команд

15. **Объединение корней сканирования**. При сканировании все значения `path` из конфигурационного файла, значения `--path` и позиционные корни CLI добавлять в один массив `Config.roots`. Любое сочетание этих способов разрешено. Сначала добавлять пути из файла в порядке записей, затем пути из CLI в порядке их обработки argp. На этапе накопления каждый переданный путь добавляет элемент массива; CLI дополняет корни из файла. Наличие обязательных корней проверять по итоговому массиву. Сохранять текущую нормализацию и повторяющиеся элементы по пункту 22. В режиме сравнения очистить `Config.roots` в памяти после полного разбора файла и CLI, до нормализации путей, проверки доступности и вывода итоговых настроек. Наличие `path` или `--path` при сравнении само по себе не является ошибкой. Позиционные аргументы в этом режиме обозначают базы данных и обрабатываются отдельно по пункту 10
16. **Параметр database при сравнении**. В режиме сравнения, выбранном через файл или CLI, игнорировать значение `database`, полученное из конфигурационного файла. Явное указание `--database` или `-d` в CLI при выбранном режиме сравнения считать ошибкой несовместимости независимо от порядка аргументов и наличия `database` в файле. При сканировании сохранять обычный приоритет CLI. Игнорирование настройки не отменяет полного чтения и проверки файла до основного разбора CLI
17. **Необязательный фильтр сравнения**. Параметр `compare-filter` разрешён в файле и CLI независимо от выбранного режима. Сам фильтр необязателен, но каждая его запись или CLI-опция должна содержать одно из значений `checksum-mismatch`, `first-source`, `second-source`. При сравнении применять объединение выбранных категорий; при полном отсутствии фильтра использовать все три категории. При сканировании допустимый фильтр не включает режим сравнения; после полного разбора файла и CLI сбросить `Config.compare_filter` в `CF_NONE_SPECIFIED`, чтобы он не влиял на работу и вывод итоговых настроек
18. **Именованные пути к сравниваемым базам**. Использовать ключи `compare-first` для первой базы и `compare-second` для второй. Добавить соответствующие CLI-параметры `--compare-first=FILE` и `--compare-second=FILE`. Каждый параметр задаёт один путь и обрабатывается как одиночное значение: последнее значение CLI заменяет значение того же ключа из файла, а повторение ключа не добавляет новую базу. Первую и вторую базы можно задать в разных источниках, например первую в файле, вторую через CLI. При использовании именованной формы проверять наличие обоих путей и отсутствие позиционных путей после объединения файла и CLI только при включённом режиме сравнения по пункту 10. Категории фильтра `first-source` и `second-source` относятся соответственно к первой и второй базам
19. **Доступность и ошибки чтения конфигурационного файла**. Если стандартный `precizer.conf` отсутствует, продолжить запуск без него. Если стандартный файл найден, но недоступен для чтения, завершить запуск с ошибкой. Если файл, явно указанный через `--config`, отсутствует или недоступен для чтения, завершить запуск с ошибкой. Если чтение началось, но завершилось ошибкой, остановить запуск; продолжать работу с частично прочитанными настройками нельзя
20. **Пути сравнения без включённого режима**. Параметры `compare-first` и `compare-second` сами не включают сравнение. Если после полного разбора файла и CLI режим сравнения не включён, очистить оба значения в памяти, в `Config`, независимо от источника. Наличие одного или обоих параметров само по себе не вызывает ошибки или предупреждения. Эти базы не открывать и не проверять на доступность. Очистка не отменяет проверку синтаксиса и значений при разборе; корни сканирования по-прежнему обязательны
21. **Сообщения об ошибках**. Для ошибок, имеющих аналог в CLI, использовать существующий текст сообщения CLI. При ошибке конкретной записи конфигурационного файла добавлять расположение записи: путь к файлу и исходный номер строки. Сохранять действующую диагностику ошибок CLI и правило для отсутствующих обязательных параметров из пункта 9. Новые сообщения без аналога в CLI писать на US English в общем стиле диагностики программы: объяснять причину ошибки и при необходимости давать короткую подсказку по исправлению. В новых сообщениях о недопустимом значении указывать имя настройки, полученное значение и допустимые варианты; при превышении длины строки — установленный предел. При смешивании именованных и позиционных путей сравнения сообщать о несовместимости и указывать обе допустимые формы передачи. Точные формулировки определять при реализации без отдельного согласования и закреплять в полных golden-шаблонах
22. **Несколько корней и дальнейшее развитие multi-root**. Наличие нескольких корней в `Config.roots` допускается и само по себе не является ошибкой конфигурации или CLI. На этапе этого плана сохранять существующий последовательный обход элементов массива, включая повторный обход повторяющихся корней, и действующее поведение БД. Такой способ передачи путей предусматривает дальнейшее развитие multi-root. Полноценный раздельный учёт файлов разных корней, изменение схемы БД, исправление очистки записей и обработку повторов реализовать на отдельном этапе развития программы; эти работы не входят в текущий план и не являются условием его завершения
23. **Очистка настроек другой операции**. После полного разбора файла и CLI очищать в памяти настройки, неприменимые к выбранному режиму, по разделу 2.2. Освобождать ненужные строки и массивы, а скалярные поля и связанные признаки возвращать к значениям по умолчанию. Правило действует независимо от источника настройки и порядка аргументов. Очистку выполнять до вывода итоговой конфигурации: неиспользуемые настройки не должны менять диагностический вывод и golden-шаблоны относительно запуска без них. Содержимое конфигурационного файла не изменять. Очистка не отменяет проверок синтаксиса и значений, ошибок несовместимости из пунктов 10 и 16 и обязательных параметров выбранной операции
24. **Пустой запуск и неполные настройки**. Если аргументов CLI нет, а стандартный файл отсутствует, пуст или содержит только пустые строки и комментарии, показывать краткую справку и завершаться успешно, как при текущем запуске `precizer` без аргументов. Если файл содержит записи настроек, но обязательных путей после объединения с CLI недостаточно, завершаться ошибкой по пункту 9. Запись с ложным значением флага тоже считается записью настройки, хотя её действие пропускается. Явное указание `--config=FILE` при недостатке обязательных путей также приводит к ошибке; пустой выбранный файл не превращает такой запуск в успешный показ справки. Если файл задаёт всё необходимое, выполнять операцию без аргументов CLI. Информационные параметры обрабатывать по пункту 25
25. **Информационные параметры**. Параметры `--help`, `--usage` и `--version` не требуют корней сканирования или путей сравниваемых баз и не запускают эти операции. При успешном предварительном проходе сохранять общий порядок: выбранный конфигурационный файл полностью прочитать и проверить до основного разбора CLI. Ошибки открытия, чтения, формата или значений файла завершают запуск до обработки информационных параметров; наличие `--help`, `--usage` или `--version` не позволяет пропустить ошибочный файл. При синтаксической ошибке предварительного прохода применять исключение из пункта 3 раздела 2: файл не читать, исходный CLI передать обычному обработчику

Правила применения `compare-filter`:

| Настройка `compare-filter` | Режим сравнения выбран через файл или CLI | Режим сканирования |
|---|---|---|
| Нигде не указана | Сравнение по всем трём категориям | Обычное сканирование |
| Допустимое значение только в файле | Применить фильтр | Очистить в памяти до вывода настроек |
| Допустимое значение только в CLI | Применить фильтр | Очистить в памяти до вывода настроек |
| Допустимые значения в обоих источниках | Объединить выбранные категории | Очистить в памяти до вывода настроек |
| Несколько допустимых значений через повторение параметра | Объединить категории; одинаковые значения допустимы | Очистить в памяти до вывода настроек |
| В файле `compare-filter =` | Ошибка | Ошибка |
| В CLI `--compare-filter=` | Ошибка | Ошибка |
| В CLI `--compare-filter` без обязательного значения | Ошибка | Ошибка |
| Недопустимое значение в любом источнике | Ошибка | Ошибка |

Каждую запись проверять отдельно: пустое, отсутствующее у явно указанной опции или недопустимое значение считать ошибкой независимо от режима. Корректное значение из другого источника не исправляет такую ошибку. Полное отсутствие параметра допустимо. Обязательные операнды сохраняются: ровно две базы для сравнения и корни для сканирования

Пример сравнения, полностью заданного в конфигурационном файле:

```ini
compare = true
compare-first = /mnt/storage/first.db
compare-second = /mnt/backup/second.db
```

При этих настройках в `precizer.conf` достаточно запуска `precizer` без аргументов. Для замены только второй базы использовать `precizer --compare-second=/mnt/backup/another.db`: режим сравнения и путь к первой базе сохраняются из файла. Сохранить этот пример в документированном файле по умолчанию по пункту 14

Примеры записи флагов:

```ini
# Параметры запуска
progress = YES # Показывать прогресс
update = 1
dry-run = false
```

В этом примере `progress` и `update` включаются, а запись `dry-run` пропускается. Она не меняет ранее установленный режим пробного запуска

Пример нескольких путей и правил фильтрации в файле:

```ini
path = /mnt/storage1
path = /mnt/storage2
ignore = ^cache/
ignore = ^tmp/
include = ^cache/keep/
include = ^tmp/keep/
```

Пример значений `ignore` со строками продолжения:

```ini
ignore = ^cache/
    ^tmp/
    ^something_eles/

ignore = ^other/
    ^things/
```

Эквивалентная запись с повторением ключа:

```ini
ignore = ^cache/
ignore = ^tmp/
ignore = ^something_eles/
ignore = ^other/
ignore = ^things/
```

В обоих случаях в список `ignore` добавляются пять отдельных выражений в указанном порядке. Оба примера сохранить в корневом `precizer.conf` с пояснением их эквивалентности

Пример выбора другого конфигурационного файла с последующим переопределением глубины сканирования через CLI:

```sh
precizer --config=profiles/archive.conf --maxdepth=2
```

## 2 Требования к реализации

1. **Разбор с помощью inih**. Использовать библиотеку inih из `libs/inih` для чтения записей `ключ = значение` без секций. Применять параметры библиотеки из раздела 2.1. Каждую строку продолжения inih передаёт отдельным вызовом обработчика с предыдущим ключом. Определение поддерживаемых настроек и их смысла реализовать в precizer
2. **Одинаковое действие параметров**. Для значений, поддерживаемых в CLI, сохранять те же правила допустимости и выполнять те же действия при чтении из файла. Момент проверки регулярных выражений зависит от источника по пункту 12 этого раздела. При ошибках использовать общие тексты сообщений с добавлением расположения записи файла по пункту 21 раздела 1. Для записи флагов в файле дополнительно поддерживать логические значения из раздела 1. Исключение для `database` при сравнении определено пунктом 16 раздела 1
3. **Два прохода argp с одной таблицей параметров**. Использовать существующую таблицу `options[]` для предварительного и основного разбора CLI. Предварительный проход выполнять с `ARGP_SILENT`: его обработчик только сохраняет путь из `--config`, остальные параметры распознаются для правильного отделения опций от их значений, но не применяются. Значения, обязательные параметры и совместимость настроек на этом проходе не проверять; сообщения и справку не выводить. При успешном проходе полностью прочитать и применить конфигурационный файл, затем выполнить основной проход. Если предварительный argp остановился на синтаксической ошибке, не разбирать её причину и не сообщать её отдельно: отбросить частично найденный путь, не читать ни стандартный, ни явно выбранный файл и сразу передать исходный CLI обычному обработчику. Основной проход сам выполняет полную проверку и формирует обычную диагностику в своём порядке; после ошибки операция не запускается. В основном проходе `--config` также разбирается, но чтения файла не вызывает. Значения по умолчанию задавать один раз при инициализации
4. **Проверка итоговых настроек**. Проверять синтаксис и отдельные значения при чтении каждого источника; для регулярных выражений применять порядок из пункта 12 этого раздела. Наличие обязательных параметров и взаимосвязи параметров проверять после объединения настроек, до начала сканирования или сравнения баз данных. Учитывать исключения для пустого запуска и информационных параметров по пунктам 24 и 25 раздела 1
5. **Разделение настроек и рабочего состояния**. Использовать файл для описания параметров запуска. Управление соединениями с базами данных, скомпилированными регулярными выражениями, состоянием транзакций и другими рабочими ресурсами оставить в программе
6. **Совместимость существующих запусков**. Сохранить существующее поведение CLI при отсутствии конфигурационного файла с учётом правил для `database`, `compare-filter` и очистки настроек другой операции из пунктов 16, 17 и 23 раздела 1. Допустимый `--compare-filter` при сканировании больше не должен вызывать ошибку. Обеспечить сканирование и сравнение без аргументов командной строки, если файл задаёт всё необходимое для выбранной операции. Пустой запуск, неполные настройки и информационные параметры обрабатывать по пунктам 24 и 25 раздела 1
7. **Общее добавление корней**. Добавить повторяемый параметр `--path=PATH`. Для `path` из файла, `--path` и позиционных корней CLI использовать общий способ добавления одного пути в `config->roots` с одинаковыми проверками значения. Сохранять порядок обработки существующего argp: порядок смешанных опций и позиционных аргументов может отличаться от их расположения в командной строке. Пустой путь не является допустимым корнем и не означает очистку массива
8. **Игнорирование файлового database**. В локальном контексте разбора достаточно одного признака явного указания `--database` или `-d` в основном проходе CLI. После полного разбора, если выбран режим сравнения и этот признак отсутствует, очистить сохранённые в памяти путь основной базы и производное имя до вывода итоговых настроек. Существующий `db_determine_name()` затем выберет служебную базу `:memory:`. Если в режиме сравнения признак установлен, выдать ошибку несовместимости. Источник включения режима — файл или CLI — на это правило не влияет. Общий механизм хранения происхождения всех настроек не требуется
9. **Применение compare-filter**. Накапливать выбранные категории в существующем поле `config->compare_filter`. После полного разбора файла и CLI сохранять их при сравнении, а при сканировании сбрасывать поле в `CF_NONE_SPECIFIED` до диагностического вывода. Удалить проверку, запрещающую корректный фильтр без режима сравнения; проверки обязательного значения опции, допустимых категорий и обязательных путей сохранить
10. **Подготовка операндов сравнения**. Именованные пути первой и второй баз сохранять в отдельных полях, чтобы CLI мог заменить каждый из них независимо; позиционные пути накапливать в существующем массиве `db_file_paths`. После полного разбора файла и CLI при включённом режиме сравнения сначала отклонить сочетание любого именованного пути с любым позиционным. Затем для именованной формы проверить наличие обоих путей и заполнить ими `db_file_paths` в порядке «первая база, вторая база»; для позиционной формы проверить наличие ровно двух элементов массива. Дальнейшая обработка использует этот массив, как существующий код сравнения. Для такой проверки учитывать источник каждого именованного значения не требуется. Если режим сравнения не включён, освободить сохранённые значения именованных путей и очистить соответствующие поля `Config` до нормализации путей и вывода итоговых настроек. Не очищать их до основного разбора CLI, поскольку он может включить сравнение

11. **Учёт записей файла для пустого запуска**. В локальном контексте разбора хранить признак наличия хотя бы одной записи настройки в файле. Пустые строки и комментарии его не устанавливают; корректная запись флага с ложным значением устанавливает его до пропуска действия. Не определять наличие записей по итоговым значениям `Config`: они могут совпасть со значениями по умолчанию или быть очищены как неприменимые к выбранной операции. Использовать этот признак вместе с наличием аргументов CLI для правила пункта 24 раздела 1
12. **Простая проверка регулярных выражений**. Каждое выражение `ignore`, `include` и `lock-checksum` из файла, включая строки продолжения, проверять сразу при чтении временной компиляцией PCRE2. При ошибке прекращать чтение и выводить существующее сообщение с путём файла и исходным номером строки. При успехе сразу освобождать временный объект и добавлять копию строки в существующий список. Использовать небольшую общую функцию компиляции одного выражения с теми же параметрами PCRE2 и текстом ошибки, что в рабочей компиляции; расположение записи передавать только при проверке файла. Рабочую компиляцию итоговых списков оставить в существующем `compile_patterns()`. Не добавлять хранение происхождения каждого выражения, признаки выполненной проверки или кеш временных объектов; повторная компиляция при запуске принимается ради простоты кода. Для выражений CLI сохранить отложенную проверку при рабочей компиляции и ранний выход для информационных параметров. Единственное дополнение: после успешного разбора, если запуск продолжается для выполнения сравнения, перед очисткой `lock_checksum` проверить весь накопленный список той же временной компиляцией, включая уже проверенные записи файла, без разделения по источникам

Эквивалентные способы передачи нескольких корней в режиме сканирования:

```sh
precizer /mnt/storage1 /mnt/storage2
precizer --path=/mnt/storage1 --path=/mnt/storage2
precizer --path=/mnt/storage1 /mnt/storage2
```

Если файл содержит `path = /mnt/archive`, во всех трёх примерах этот корень добавляется перед `/mnt/storage1` и `/mnt/storage2`

Объединение источников формирует входной массив корней и передаёт его существующему обходу по пункту 22 раздела 1. До отдельного этапа multi-root сохраняются известные ограничения: одинаковые относительные пути разных корней используют общую запись БД, а очистка при `--update` проверяет записи относительно одного корня. Эти ограничения принимаются для текущего этапа и не блокируют поддержку конфигурационного файла. Дальнейшая реализация multi-root описана в в отдельном проекте и к текущей реализации не имеет отношения.

### 2.1 Настройки inih

Определить параметры библиотеки через `#define` в основном заголовочном файле приложения `src/precizer.h` перед подключением `ini.h`. Значения параметров не передавать через аргументы компилятора и не дублировать в Makefile

```c
#define INI_MAX_LINE 4096
#define INI_STOP_ON_FIRST_ERROR 1
#define INI_HANDLER_LINENO 1
#define INI_ALLOW_MULTILINE 1
#define INI_ALLOW_INLINE_COMMENTS 0
#define INI_START_COMMENT_PREFIXES "#"
#define INI_USE_STACK 1
```

- `INI_MAX_LINE=4096` — фиксированный буфер размером 4096 байт. Допускать до 4093 байт содержимого каждой физической строки, оставляя место для `\r`, `\n` и завершающего нулевого байта. Ограничение применять к каждой строке продолжения отдельно. Более длинную строку отклонять с ошибкой, не применяя обрезанное значение
- `INI_STOP_ON_FIRST_ERROR=1` — прекращать разбор на первой ошибке и завершать запуск
- `INI_HANDLER_LINENO=1` — передавать номер строки обработчику. В сообщениях об ошибках записей указывать файл и номер строки
- `INI_ALLOW_MULTILINE=1` — поддерживать строки продолжения по пункту 13 раздела 1
- `INI_ALLOW_INLINE_COMMENTS=0` — отключить встроенную обработку комментариев после значения. Обработку `#` в любом месте строки выполнять в precizer при подготовке входных строк
- `INI_START_COMMENT_PREFIXES="#"` — использовать только `#` для комментариев на отдельных строках. Символ `;` сохранять как часть значения
- `INI_USE_STACK=1` — использовать фиксированный буфер на стеке без динамического выделения памяти для него

Остальные параметры inih оставить со штатными значениями по умолчанию

Определения из `src/precizer.h` должны действовать до первого подключения `ini.h` как в приложении, так и при компиляции реализации inih. Одного подключения заголовка в приложении недостаточно: `ini.c` собирается отдельно. В частности, `INI_HANDLER_LINENO` меняет число аргументов обработчика и должен совпадать у библиотеки и вызывающего кода

### 2.2 Очистка настроек по выбранной операции

Очищать только настройки, неприменимые к выбранной операции целиком. Отсутствие подходящих файлов или других условий для действия параметра в конкретном запуске не является основанием для общего сброса настроек

| Выбранная операция | Поля `Config` | Состояние после очистки |
|---|---|---|
| Сравнение | `roots` | Освободить элементы и хранилище массива, оставить корректный пустой массив с нулевой длиной |
| Сравнение | `maxdepth` | `-1`, как при инициализации |
| Сравнение | `force`, `quiet_ignored`, `watch_timestamps`, `one_file_system`, `db_drop_ignored`, `db_drop_inaccessible`, `rehash_locked` | `false` |
| Сравнение | `lock_checksum`, `lock_checksum_pcre_compiled` | Освободить выделенные ресурсы, оставить `NULL` |
| Сравнение | `progress`, связанный `show_remembered_messages_at_exit` | `false` до начала выполнения операции |
| Сравнение | `dry_run_with_checksums` | `false`; значение `dry_run` сохранить |
| Сравнение | `db_primary_file_path`, `db_file_name`, полученные из файлового `database` | Очистить по пункту 8 раздела 2; явный CLI-параметр `--database` или `-d` по-прежнему вызывает ошибку |
| Сканирование | Именованные пути `compare-first` и `compare-second`, массив `db_file_paths` и производные имена `db_file_names` | Освободить сохранённые значения, оставить пустые поля и массивы |
| Сканирование | `compare_filter` | `CF_NONE_SPECIFIED` |

При сравнении сохранять `ignore`, `include` и согласованный с ними `include_specified`: эти фильтры используются для отбора сравниваемых записей. Сохранять `db_check_level`, управляющий проверкой целостности обеих баз, и общие настройки вывода: `verbose`, `silent`, `color` и связанные настройки логирования

`update` и `dry_run` также сохранять: в текущем коде сравнение вызывает проверку версии БД и её обновление через `db_integrity_check()`, `db_check_version()` и `db_upgrade()`. Флаг `update` разрешает обновление старой версии, а `dry_run` влияет на проверку и операции с БД. Они не являются неиспользуемыми настройками обхода. При этом `dry_run_with_checksums` применяется только при чтении файлов: после его очистки в режиме сравнения `dry-run=with-checksums` остаётся обычным `dry-run` и так отображается в диагностике

Очистку выполнять в одном месте после полного разбора и проверок обязательных параметров и запрещённых сочетаний, до нормализации путей, создания производных имён, компиляции используемых шаблонов и вызовов `parse_arguments_show_testing_diagnostics()` и `parse_arguments_show_verbose_diagnostics()`. Не очищать настройки при чтении файла или при встрече `--compare`: последующие аргументы ещё могут влиять на итоговое состояние. Повторно вызывать `init_config()` или обнулять весь `Config` нельзя

Сохранить проверку значений перед очисткой. Перед удалением `lock_checksum` при сравнении проверить весь накопленный список по пункту 12 раздела 2. Эту проверку и очистку выполнять после раннего выхода для информационных параметров, чтобы сохранить существующее поведение CLI. Ошибки выражений из файла выявляются ещё при чтении и не позволяют перейти к основному разбору CLI

Предупреждения о `--db-drop-inaccessible` без `--update` и `--rehash-locked` без `--lock-checksum` проверять только при сканировании после определения режима. При сравнении соответствующие настройки очищаются и сами по себе не вызывают предупреждений. При сканировании сохранить существующие предупреждения и поведение этих сочетаний

Для управляемых массивов использовать существующие функции освобождения, сохраняющие корректное пустое состояние. Последующее освобождение `Config` должно оставаться безопасным. Не подменять очистку условным скрытием строк в функциях вывода

## 3 Пошаговая реализация

Выполнять этапы последовательно, сохраняя работоспособность существующих запусков после каждого изменения. Внутри этапа переносить обработку параметров небольшими группами и проверять каждое завершённое изменение

### 3.1 Подключить inih к сборке приложения и тестов

Добавить `inih` в `LIBS` и `STATLIBS` основного `Makefile` и в `LIBS` файла `tests/Makefile`. Использовать существующую библиотеку из `libs/inih`, уже включённую в `libs/Makefile`

Добавить в `src/precizer.h` определения из раздела 2.1. Обеспечить их подключение при компиляции реализации inih до первого включения `ini.h`, без дублирования значений в аргументах сборки. Учесть зависимости заголовка приложения и обеспечить пересборку библиотеки при изменении этих определений

Результат: приложение и тесты собираются с inih. Чтение конфигурации подключается на последующих этапах

Проверка: существующие тесты проходят после изменения состава библиотек. Приложение и реализация inih используют одинаковые определения из `src/precizer.h`, в том числе одинаковую сигнатуру обработчика с номером строки

### 3.2 Подготовить общую обработку значений

Начать с одного параметра — `maxdepth`. Вынести преобразование, проверку и применение его значения из `parse_opt()` в небольшую общую функцию и вызывать её из существующего обработчика CLI. Сохранить допустимые значения и сообщения об ошибках

Затем тем же способом переносить остальные параметры: сначала одиночные значения, затем флаги и повторяемые параметры. Каждый перенос выполнять отдельным небольшим изменением. Сохранять все действия параметра, включая связанные настройки: например, `progress` включает повторный вывод сохранённых сообщений, а `dry-run=with-checksums` — пробный запуск и вычисление контрольных сумм

Для логических значений файла использовать единое распознавание вариантов из пункта 12 раздела 1. При истинном значении вызывать существующее действие включения флага, при ложном — пропускать запись. Благодаря этому для чтения файла используются действующие обработчики CLI без добавления обратных действий для флагов и связанных настроек

Обработку событий argp, справку, позиционные аргументы и итоговые проверки оставить в `parse_opt()`. Общие функции должны принимать значения независимо от источника, чтобы их мог вызывать обработчик конфигурационного файла

Для регулярных выражений выделить небольшую общую функцию компиляции одного выражения по пункту 12 раздела 2. Использовать её для временной проверки и в существующей рабочей компиляции, сохранив параметры PCRE2 и основной текст ошибки. Временный объект сразу освобождать; JIT-компиляцию оставить только при подготовке рабочих выражений в `compile_patterns()`. Обычное добавление выражения из CLI в список не должно запускать его немедленную проверку
